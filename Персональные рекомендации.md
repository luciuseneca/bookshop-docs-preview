# Персональные рекомендации

## 1. Возможности

На главной странице покупатель с действующим JWT видит блок **«Рекомендации для вас»**. Лента смешивает персональный подбор, популярные книги, новинки и случайные находки. В странице до 20 карточек, следующие страницы подгружаются при прокрутке. Покупатель с пустой историей тоже получает подборку. Отдельный блок «Популярное» на главной доступен и гостю. [Шаблон главной](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/templates/index.html)

По мере действий покупателя лента учитывает его категории, авторов и поисковые фразы. События обрабатываются в фоне, поэтому текстовый профиль и вектор могут обновиться в разное время. Популярность считается раз в сутки. В API есть ручная постановка этой задачи и тестовый приём событий.

## 2. Сквозной сценарий (E2E)

Покупатель `42` ищет «космос» в категории «Фантастика», дважды открывает книгу `101` и добавляет её в избранное. У книги `category_id=7` и `author_id=19`. На следующее утро покупатель возвращается на главную и листает ленту. Идентификаторы, значения сигналов и подборки ниже условные. В запросах используется префикс `/api` из конфигурации примера.

### 1. Покупатель ищет и открывает книгу

Браузер отправляет `GET /api/books/categories/fantastika/title?title=космос` с Bearer-токеном. FastAPI получает `user.sub=42` из JWT. В `CategoryBooksSearchQH.by_title(filters, pagination)` приходят `filters` (Pydantic-модель) с `category_slug="fantastika"` и `title="космос"`, а курсор первой страницы равен `None`. Elasticsearch возвращает ID совпадений, PostgreSQL отдаёт данные для карточек, обработчик восстанавливает порядок релевантности. Если вернулось три карточки, API отправляет `CustomerPersonalRecoEVENT` (Pydantic-модель) с `type="search"`, `user_id=42`, `book_id=None` и `metadata={"query":"космос","results_count":3}` (JSON-объект). **Событие пишется на первой странице**, даже если она пустая. Поиск по автору работает так же с параметром `name`. Ветвь поиска по стране событие не публикует. [Обработчик поиска](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/product/service/infrastructure/query_handlers/book/search.py) · [Маршруты поиска](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/product/api/routers/book.py#L171-L259)

Покупатель дважды запрашивает `GET /api/books/orbita`. `BookDetailQH.get_book(book_slug="orbita")` возвращает карточку с `id=101`, а роутер на каждый успешный запрос публикует `view` с `book_id=101` и пустым `metadata`. После `POST /api/books/wishlist?book_id=101` вызов `AddBookToWishlist.add(user_id=42, book_id=101)` сохраняет связь в `wishlists` (таблица PostgreSQL). Затем API публикует `wishlist_add` и возвращает `201`. Просмотры и поиски отслеживаются только для покупателя. [Маршрут карточки](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/product/api/routers/book.py#L106-L132) · [Маршруты избранного](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/order/api/routers/wishlist.py#L35-L99)

| Действие | `type` (значение Python Enum) | Вес |
| --- | --- | ---: |
| Карточка книги | `view` | 0,5 |
| Поиск по названию или автору внутри категории | `search` | 0,3 |
| Добавление в избранное / удаление из него | `wishlist_add` / `wishlist_remove` | 1,5 / −0,5 |
| Добавление в корзину | `cart_add` | 2,0 |
| Успешная запись отзыва | `rating` | `(rating - 3) * 0.75` |
| События, принимаемые тестовым маршрутом без подтверждённого издателя в штатных сценариях | `cart_remove` / `purchase` / `share` / `preview` | −0,3 / 3,0 / 1,2 / 0,8 |

Вес лежит в `USER_EVENT_WEIGHTS` (словарь Python) с резервным значением `0.5`. Для оценки `5` вес равен `1.5`, для оценки `1` — `-1.5`. Штатная публикация отзыва проверяет диапазон 1–5 через `BookRatingEventMeta` (Pydantic-модель). Обработчик события преобразует `metadata["rating"]` в число и сохраняет вес `0.0`, если значения нет или оно не преобразуется. Тот же конвейер можно вызвать через `POST /api/books/events/fdkhefkewqf/fdwowehfkwef/fwlkehfkwe` с JWT покупателя и телом `{"type":"rating","book_id":101,"metadata":{"rating":5}}`. Входная модель `BookPersonalRecoEVENT` (Pydantic-модель) принимает enum `type`, необязательный `book_id` и произвольный словарь `metadata` с пустым значением по умолчанию. Сервер подставляет ID из токена и после успешной публикации отвечает `202 {"status":"accepted"}`. Запись в БД выполняется позже. Ошибку публикации этот маршрут пробрасывает. ### 2. RabbitMQ передаёт события, обработчик записывает историю

Для первого просмотра роутер вызывает `publish_user_personal_books_reco_rmq_safe(routing_key="events.view", event=event, correlation_id="42")`. Через aio-pika он ждёт публикации JSON-сообщения с режимом `PERSISTENT` в `user_events` (durable topic exchange RabbitMQ). Ожидание ограничено стадией публикации, а результат обработки HTTP-запросу не нужен. При исключении публикации обёртка пишет ошибку в лог, и покупатель всё равно получает карточку или результат уже выполненного действия.

Отдельный процесс `recommendation_consumer` принимает сообщения из `personal_book_reco` (durable очередь RabbitMQ), привязанной по `events.#`, с `prefetch_count=10`. Он вызывает `CustomerPersonalRecoEVENT.model_validate_json(message.body)` и передаёт объект в `BookPersonalRecoForCustomerUC.generate(event)`. `message.process(requeue=False)` подтверждает успешную обработку. При проброшенном исключении сообщение отклоняется без повтора и через `user_events_dlx` (fanout exchange RabbitMQ) попадает в `personal_book_reco_dlq` (очередь RabbitMQ для отклонённых сообщений). [Издатель](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/user/service/infrastructure/rabbitmq/producer/reco_events.py) · [Топология и обработчик](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/product/service/infrastructure/rabbitmq/book/consumers/personal_reco.py)

Для `view` с ID книги обработчик делает `SET event_dedup:42:101:view 1 NX EX 60`. Первый просмотр создаёт ключ (строка Redis). Если второе сообщение обработано в эти 60 секунд, ключ уже есть, и обработчик завершает его успешно **без второй записи и нового пересчёта**. Оба HTTP-ответа при этом содержат карточку. Проверка выполняется до транзакции. Если запись первого просмотра упадёт, ключ дедупликации всё равно доживёт до истечения TTL.

Для принятого просмотра обработчик вызывает `get_category_and_author_id_by_book_id(book_id=101)`, получает `7` и `19` и в транзакции SQLAlchemy сохраняет `CustomerEventModel` (ORM-модель) в `user_events` (таблица PostgreSQL). Колонки `user_id`, `book_id`, `event_type`, `category_id`, `author_id`, `weight`, `created_at` и `metada` сохраняют контекст для дальнейших расчётов. Для поиска с `book_id=None` категория и автор остаются `NULL`, а фраза и число результатов лежат в `metada` (JSON-колонка). [Запись, дедупликация и вес события](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/product/service/usecase/book/personal_reco.py#L38-L220)

### 3. События обновляют профиль и запускают отложенный пересчёт

После коммита каждого принятого события `invalidate(user_id=42)` удаляет `user_reco_profile:42` и `user_reco_vector:42` (строки Redis с JSON-объектом профиля и JSON-массивом вектора, TTL каждого — час). `_update_user_reco_profile(user_id=42)` увеличивает `user_reco:42:version` (счётчик Redis с TTL 30 дней) и ставит `user_reco:42:pending` (строка Redis, `SET NX`, TTL 120 секунд). Для чистого счётчика принятые поиск, просмотр и избранное дадут версию `3`. Ошибки инвалидации и планирования логируются после коммита, запись события остаётся в PostgreSQL.

Первый успешный `SET NX` вызывает `CustomerTaskiqSchedulesPublisher.update_user_reco_profile(user_id=42)`. Тот ставит задачу через `.kicker().with_labels(delay=30).kiq(42)`. Taskiq использует RabbitMQ с плагином отложенной доставки. Следующие события при существующем `pending` продлевают его TTL и обновляют версию. Срок доставки уже поставленной задачи отсчитывается **от первой постановки**. Это позволяет объединить поиск, просмотр и избранное в один запуск. [Постановка пересчёта](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/product/service/usecase/book/personal_reco.py#L221-L257) · [Планировщик пользователя](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/user/service/infrastructure/taskiq/schedules/customer/base.py)

`CustomerPersonalBooksRecoProfile.get(user_id=42)` читает профиль из Redis или берёт **200 последних событий** через `get_list_by_user_id_by_new(user_id=42)`. Вес вклада в категорию и автора равен `event.weight * exp(-age_days / 30)`, где возраст считается целыми днями. Через 30 дней вклад события с весом `1.5` упадёт примерно до `0.55`. В день событий просмотр и избранное дадут категории `7` и автору `19` по `2.0`. Удаление из избранного уменьшило бы обе суммы на `0.5`.

`CustomerRecoProfileDTO` (dataclass Python) хранит `category_scores` и `author_scores` (словари ID → вес), по пять лидеров в `top_categories` и `top_authors` (списки ID), до десяти уникальных недавних фраз в `recent_searches` (список строк), `interacted_books` и `purchased_books` (списки уникальных ID). В примере это `[7]`, `[19]`, `["космос"]`, `[101]` и `[]` соответственно. Вес поиска с пустыми ID категорий и авторов не влияет на их суммы. Фраза попадёт в текст для эмбеддинга, а `results_count` остаётся в истории. При чтении вектор берут из Redis или через `retrieve(ids=[42], with_vectors=True)` из `user_reco_profile` (коллекция Qdrant), после чего найденный вектор снова кешируют. До пересчёта там может лежать предыдущий вектор. Если точку ещё ни разу не записывали, лента подбирает книги по уже известным категориям. [Сборка и чтение профиля](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/user/service/infrastructure/customer/reco_profile.py#L157-L364)

### 4. Воркер сохраняет новый вектор

Воркер Taskiq запускает `update_user_reco_books_profile_schedule(user_id=42)`, а тот вызывает `build(user_id=42)`. Метод ставит `user_reco:42:lock` (строка Redis, `SET NX EX 600`). Пока ключ существует, второй запуск для того же покупателя сразу завершится. TTL освобождает ключ при зависании, штатное освобождение идёт в `finally`. После проверки `pending` метод читает начальную версию, например `3`, и вызывает `_update_profile(user_id=42)`.

1. Метод берёт до 50 недавних уникальных `interacted_books` и запрашивает `books_qdrant_repo.get(point_ids=[101], with_vectors=True)`. В `books` (коллекция Qdrant с косинусной метрикой) у книги уже должен быть вектор длиной 1024. При индексации Ollama с моделью `bge-m3` получает заголовок, автора, категорию, год при наличии и до 1000 символов описания. Если профилю недостаёт книжных векторов, пересчёт выходит без новой записи. Одного поискового запроса для построения вектора мало.
2. `get_weights_by_book(user_id=42, book_ids=[101])` суммирует веса всех сохранённых событий для этих книг без затухания по возрасту. Сумма ограничивается диапазоном `[0.1, 3.0]`, а при отсутствии суммы используется `0.1`. NumPy считает `np.average(vectors_np, axis=0, weights=weights_np)`. Для одной книги вес `2.0` даёт её собственный вектор. При нескольких книгах больший вес сильнее смещает среднее. Даже отрицательная сумма превращается в малый положительный вес.
3. Метод подставляет имена авторов и названия категорий из PostgreSQL, до пяти описаний по 300 символов и фразы из профиля. `OllamaEmbedder.embed(text)` отправляет `POST /api/embed` с `model="bge-m3"` и `input=[text]`. NumPy складывает **70% среднего по книгам и 30% эмбеддинга текста**, делит результат на L2-норму, если она больше нуля, и преобразует его в список чисел.
4. Метод сначала записывает новый вектор в Redis, затем делает Qdrant `upsert(wait=True)` точки с `id=42`, `vector` (список чисел) и `payload={"top_categories":[7],"top_authors":[19]}` (словарь метаданных). Следующий запрос ленты уже может использовать этот вектор.

В конце воркер читает версию снова и снимает `pending`. Если во время работы пришло событие и версия стала `4`, воркер пытается заново поставить `pending` и при успехе планирует ещё один запуск. Так события, замеченные между чтениями версии, получают ещё один пересчёт. Сравнение версии и удаление флага идут отдельными командами. Сбой после записи в Redis может оставить кеш новее Qdrant до успешной повторной записи. Для задачи включены повторы `retry_on_error=True` с `max_retries=3`. Каждый повтор всё равно проверяет `pending`. [Пересчёт и проверка версии](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/user/service/infrastructure/customer/reco_profile.py#L366-L593) · [Конфигурация задачи](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/user/service/infrastructure/taskiq/schedules/customer/update_customer_recs_vector.py)

### 5. Ночной пересчёт добавляет книге дневной балл

После окончания дня Taskiq Scheduler ставит `update_books_popularity()` по cron `10 0 * * *` (**00:10 UTC, 03:10 по Москве**). Воркер считает предыдущие календарные сутки UTC, от полуночи включительно до следующей полуночи исключительно. Дата события берётся из `created_at` в PostgreSQL.

Допустим, за эти сутки у книги `101` есть две строки в `order_items` (таблица PostgreSQL) с `quantity=4` и `quantity=1`, одна запись в `wishlists`, один новый отзыв в `reviews` (таблица PostgreSQL), рейтинг книги `4.0` в `books` (таблица PostgreSQL) и три разных авторизованных зрителя, включая покупателя `42`.

| Сигнал | Что считает SQL | Вклад |
| --- | --- | ---: |
| Позиции заказа | `COUNT(1)` по строкам `order_items`. SQL не суммирует `quantity` и не проверяет оплату | `2 × 0.60 = 1.20` |
| Избранное | Сохранившиеся строки `wishlists`, созданные за сутки | `1 × 0.30 = 0.30` |
| Отзывы | Строки `reviews`, созданные за сутки | `1 × 0.05 = 0.05` |
| Рейтинг | Текущий `books.rating`. При `NULL` берётся ноль | `4.0 × 0.05 = 0.20` |
| Просмотры | `COUNT(DISTINCT user_id)` по сохранённым `view` за сутки для этой книги | `3 × 0.10 = 0.30` |

Итог **`popularity_score=2.05`**. Повторный просмотр тем же покупателем после истечения 60 секунд может попасть в историю, но суточный балл по просмотрам останется прежним. Книга участвует, если доступна и за сутки есть хотя бы одна позиция заказа, запись избранного, отзыв или просмотр. Одного рейтинга для создания строки недостаточно.

Задача читает строки через `session.stream(stmt)` партиями по 1000 и делает `INSERT … ON CONFLICT (book_id, stat_date) DO UPDATE` в `book_popularity_stats` (таблица PostgreSQL). Сохраняются `sales`, `wishlist_adds`, `reviews` и итоговый балл. Число просмотров входит в балл, отдельного столбца для него нет. Повторный запуск обновляет строки за ту же дату, которые снова попали в выборку. Коммит общий для всех партий, при ошибке выполняется rollback. Ручной `POST /api/books/update-books-popularity/23edded/dwefewfew/dqwfqwfwqf` вызывает `update_books_popularity.kiq()` без параметра даты и отвечает `202 {"status":"queued","task":"update_books_popularity"}`. У этого маршрута в коде нет зависимости авторизации. [Расчёт и запись статистики](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/product/service/infrastructure/taskiq/tasks/book/update_popular_books.py) · [Ручной запуск](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/product/api/routers/book.py#L262-L277)

### 6. Главная запрашивает первую страницу, сервер собирает четыре подборки

Браузер вызывает `GET /api/books/main/recommendations` без `encoded_cursor`. FastAPI через Dishka получает `BooksMainRecommendationsQH` и вызывает `for_user(user_id=42, encoded_cursor=None)`. Сначала `INCR` увеличивает `book_reco:new_sessions_rate:42` (счётчик Redis). Первый запрос ставит TTL 60 секунд. Шестнадцатый старт в этом окне получает **HTTP 429**. Лимит сдерживает рост числа ключей сессий при частых перезагрузках. Запросы с курсором этот счётчик обходят. Новый `BookMainRecoCursorDTO` (dataclass Python) получает `session_id=uuid.uuid4().hex`, 32-битный `seed` (в примере `42`), `page=0` и начальный режим `vector`.

После чтения профиля и недавних показов `asyncio.gather(..., return_exceptions=True)` запускает четыре источника параллельно.

| Источник | Номинал | Как получает кандидатов |
| --- | ---: | --- |
| Персональный | 8 | `recommendations_for_user_profile(vector=profile.vector, limit=80, exclude_ids=None)` передаёт вектор в Qdrant `query_points(query=vector, limit=80, with_payload=True)`. Qdrant возвращает `ScoredPoint` (модели результата) с ID, косинусным `score` и полями `category_id`, `author_id` в метаданных. Сервер умножает `score` на `1 + 0.15` за категорию из первой тройки и добавляет к множителю `0.10` за автора из первой тройки. Например, `0.80` при обоих совпадениях становится `1.00`. Отобранные книги ограничиваются двумя на категорию и двумя на автора, затем при нехватке лимиты ослабляются. |
| Популярные | 6 | `popularity_window_subquery()` (SQL-подзапрос) суммирует дневные баллы за 7 календарных дней, считая от последней даты статистики включительно. Так при пропуске ночной задачи лента использует накопленные баллы. Сервер берёт до 60 доступных кандидатов с положительной суммой, сортирует по баллу и ID по убыванию, сэмплирует с весом по баллу. |
| Новинки | 4 | До 12 доступных книг по убыванию `id`, в примере из категории `7`. Сервер сэмплирует с весом `1 / (rank + 1)` и сначала берёт до двух из категории. Если все кандидаты из фантастики, оставшиеся места добираются из той же категории. Новизна определяется ID добавления книги в каталог. |
| Случайные находки | 2 | По `seed` генерируется старт в 63-битном диапазоне. PostgreSQL читает доступные книги с `random_key > start_key` по возрастанию индексированного `random_key`. Если строк нет, запрос начинает с начала диапазона. |

Если в истории есть `purchase`, персональный источник исключает эти ID вместе с уже выданными в сессии. Другие три источника получают исключения сессии. Обычный поиск Qdrant выполняется заново с исключениями: `personalized_offset` увеличивается на 8 на каждой успешной векторной странице и служит порогом смены режима. В Qdrant этот счётчик как SQL-подобный offset не передаётся. ### 7. Сервер выдаёт карточки и курсор, браузер догружает ленту

Взвешенный отбор `_weighted_sample` использует `random.Random(seed ^ page)` и `choices` с возвращением. Затем убирает повторы по ID и при необходимости добирает из исходного списка. Книга с высоким весом имеет больше шансов попасть в результат, а неизменный набор кандидатов при том же `seed` и номере страницы даёт воспроизводимый порядок.

`BookMainRecoBlender.mix(slots, seed=42, page=0)` перемешивает 20 мест четырёх типов. Он использует `BookBlenderSlotsDTO` (dataclass с четырьмя списками ID). Для каждого места берёт первую ещё не использованную книгу нужного типа. Если подходящих нет, перебирает остальные источники в порядке **персональный → популярные → новинки → случайные**. При списках `102–109`, `[101, 201, 202, 203, 204, 205]`, `301–304` и `[401, 402]` начало выдачи будет `[401, 102, 301, 103, 101, …]`. Книга `101` попала из популярной части. При пересечении источников она заняла бы максимум одно место.

`get_preview_by_ids(book_ids=merged_ids)` получает ORM-модели книг и их связи с авторами и категориями из PostgreSQL. Сервер восстанавливает смешанный порядок и отдаёт `BooksMainRecoRESP` (Pydantic-модель) с `books` (массив превью с ID, названием, ценой, автором, категорией и другими полями карточки) и `next_cursor` (строка или `null`). Для учёта показов он записывает **смешанные ID** до HTTP-ответа, даже если какую-то книгу не удалось дочитать из БД.

| Память показов | Как обновляется | Что меняет при следующем запросе |
| --- | --- | --- |
| `book_reco:seen:<session_id>` (список Redis) | `RPUSH`, затем `LTRIM` до 400 последних ID, `EXPIRE 1800` после непустой выдачи | Источники исключают недавние ID текущей сессии. При истечении TTL или вытеснении старых ID книга может появиться снова. `RPUSH` сохраняет оба параллельных добавления, но два одновременных запроса могут прочитать один и тот же список до записи и выбрать одинаковые книги. |
| `book_reco:impressions:42` (список Redis) | Те же операции, до 300 последних записей и TTL всего списка 3 суток от его обновления | При чтении получается множество ID. В персональном источнике и новинках вес ранее выданной книги умножается на `0.25`, например `1.00 → 0.25`. Это снижает вероятность повторного показа и оставляет книгу в пуле. Популярные и случайные находки этот множитель не используют. |

Курсор содержит `session_id`, `seed`, номер следующей страницы, персональный режим и счётчики, границу популярности `(popular_last_score, popular_last_book_id)`, `new_last_id` и `exploration_last_random_key`. Для новинок граница берётся как минимальный выбранный источником ID, для случайных находок — последний выбранный ключ. Популярный источник берёт границу из отобранных книг по минимуму пары `(score, -id)`. Следующий запрос берёт меньший балл, а при равном балле — меньший ID.

`encode()` кодирует JSON в URL-safe Base64 и дописывает HMAC-SHA256 с секретом приложения. Это позволяет серверу проверить целостность токена. Браузер передаёт ответный `next_cursor` как `encoded_cursor` при следующей прокрутке. Сервер проверяет подпись и основные поля, подменённый токен получает **HTTP 400**. Браузер добавляет новые карточки в «Рекомендации для вас». При пустой выдаче приходит `{"books":[],"next_cursor":null}`, и подгрузка заканчивается. ## 3. Другие случаи

### 1. У покупателя ещё нет истории, а дневная статистика пуста

Покупатель `77` с пустыми `top_categories` и `vector=None` открывает главную. `BookColdCandidatesProvider.get()` собирает до 200 доступных книг по `total_sales` и до 100 с наибольшими ID. Источник убирает дубли и на 10 минут кеширует общий пул в `book_reco:cold_candidates:v2` (строка Redis с JSON-массивом). При равных продажах сортировка по `random_key` даёт срез разных частей каталога. Качество сглаживается к среднему рейтингу пула по формуле `(10 * mean + rating * votes) / (10 + votes)`. Реализация берёт для сглаживания `sum_ratings` (сумма баллов), хотя счётчик голосов в модели хранится в `total_ratings`. Рейтинг после сглаживания и `log1p(total_sales)` делятся на свои максимумы в пуле, новизна берётся из нормированного ранга ID. Вес холодного персонального подбора равен `0.1 + 0.6·quality + 0.2·sales + 0.1·freshness`. База `0.1` даёт шанс старым книгам даже при нулевых рейтингах и продажах.

Популярный источник при пустом начальном запросе к статистике берёт тот же пул с весом `0.1 + 0.25·quality + 0.55·sales + 0.1·freshness` и отдельной добавкой к seed. Обе ветки сначала берут до двух книг на категорию и автора, затем ослабляют пределы при нехватке. Новинки и случайный источник тоже участвуют. Покупатель получает карточки, если в каталоге есть подходящие книги. Если покупатель уже открыл книгу категории `7`, а вектор ещё не готов, персональная ветка выбирает только доступные книги известных категорий. Она сортирует их по рейтингу, продажам и `random_key`, затем сэмплирует с весом по позиции и штрафом за показ. ### 2. Векторный источник исчерпался или дал ошибку

Пусть профиль покупателя `42` прочитан, а Qdrant после исключений вернул **пять** книжных точек при лимите страницы персонального источника `8`. Он переключается на коллаборативную ветку даже при пяти пригодных точках. Та же ветка используется при `personalized_offset >= 200` или если в курсоре уже стоит режим `collaborative`.

`find_similar_users(vector=profile.vector, limit=50, exclude_id=42)` ищет похожих покупателей в Qdrant и берёт их оценки сходства и `top_categories`. Например, профиль со сходством `0.8` и категориями `[7, 9]` даёт категории `7` вес `0.8`, категории `9` — `0.4`. Сосед со сходством `0.6` и списком `[9]` поднимает категорию `9` до `1.0`. Сервер суммирует такие вклады и передаёт `category_ids=[9, 7]` в новый запрос книжных векторов по **вектору самого покупателя** с прежними исключениями и лимитом 80. Это способ расширить тематику за счёт соседей. Книги, купленные соседями, напрямую не читаются. Курсор запоминает `collaborative` и увеличивает `collaborative_offset` на 8. Каждые три коллаборативные страницы алгоритм переходит к следующей десятке категорий, а при пустом диапазоне возвращается к первой десятке.

Если книжный запрос в Qdrant **выбросил исключение** уже после чтения профиля, `gather` передаёт ошибку сборщику. Он логирует сбой, подставляет пустой список и сохраняет прежнюю позицию источника. При шести популярных, четырёх новинках и двух случайных книгах без пересечений браузер получит **12 карточек** и курсор. При сбое чтения самого профиля до запуска источников эта защита не срабатывает.
