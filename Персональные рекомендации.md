# Персональные рекомендации

Разбор реализации [fastapi-bookshop на коммите `e281be0`](https://github.com/luciuseneca/fastapi-bookshop/commit/e281be01f267ee0a3215f61e1cf6312b33434ba6).

## Возможности

- На главной странице покупатель после входа получает ленту «Рекомендации для вас» с автоматической подгрузкой при прокрутке. На странице до 20 мест, из которых 8 отведены персональной подборке, 6 популярным книгам, 4 новинкам и 2 случайным находкам. Для гостя доступен отдельный блок «Популярное».
- Персональная подборка опирается на историю действий, интерес к категориям и авторам, поисковые фразы и близость книжных эмбеддингов к вектору покупателя. При необходимости система использует интересы похожих покупателей. Свежий аккаунт получает смешанную ленту сразу.
- Обычные действия на витрине пополняют историю в фоне. Для проверки есть тестовый API приёма событий. Популярность считается по данным всего магазина за предыдущие сутки, а в ленту попадает сводка за семь дней. Задачу можно поставить в очередь вручную.

## Сквозной сценарий (E2E)

Покупатель `user_id=42` ищет в категории «Классика» письма, открывает условную книгу №101 «Письма к Луцилию» (`category_id=7`, `author_id=11)), обновляет её страницу и добавляет книгу в избранное. Пока система пересчитывает профиль, он открывает ещё и книгу №102 (`category_id=9`, `author_id=12`). На следующее утро он возвращается на главную и листает рекомендации. ID, время, кандидаты и оценки ниже заданы для примера. В HTTP-путях используется префикс `/api` из конфигурации проекта.

### 1. Покупатель ищет и открывает книгу

Браузер отправляет `GET /api/books/categories/classics/title?title=Письма` с Bearer-токеном. FastAPI получает покупателя через `auth_user_optional`. В обработчике `CategoryBooksSearchQH.by_title(filters, pagination)` поле `filters.title` становится аргументом `query="Письма"` вызова `BooksElasticREPO.search_ids_in_category(category_slug="classics", field="title", query="Письма", encoded_cursor=None)`. Elasticsearch ищет по словам с учётом опечаток и по префиксу, фильтрует доступные книги категории и возвращает ID по релевантности. SQLAlchemy загружает по ним книги из `books` (таблица PostgreSQL), после чего обработчик восстанавливает порядок Elasticsearch. Пусть в первой странице вернулось три книги. [Код поиска](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/product/service/infrastructure/query_handlers/book/search.py#L45).

Дальше роутер формирует `CustomerPersonalRecoEVENT` (Pydantic-модель) с `user_id=42` из `user.sub`, `type=SEARCH`, `book_id=None` и `metadata={"query":"Письма","results_count":3}` (`dict` в модели, JSON-объект при передаче). Сигнал записывается для первых страниц поиска по автору и названию, включая пустую выдачу. При передаче `encoded_cursor` API пропускает публикацию, чтобы учесть поиск один раз. В текущем шаблоне категории есть расхождение: браузер отправляет `id_cursor`, а API ожидает `encoded_cursor`. Поэтому при прокрутке результатов с продолжением браузер может снова получить первую страницу и записать повторный `SEARCH`. У поиска по стране своей публикации нет. [Обработчики поиска](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/product/api/routers/book.py#L170) · [Параметр в шаблоне категории](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/templates/product/category.html#L58).

Через пять секунд покупатель открывает карточку. Браузер делает `GET /api/books/pisma-k-lutsiliyu`. FastAPI вызывает `BookDetailQH.get_book(book_slug)`, возвращает сведения о книге и публикует событие `VIEW` с `book_id=101`. При обновлении через пять секунд карточка загружается снова и роутер публикует второй `VIEW`. При `POST /api/books/wishlist?book_id=101` обработчик `AddBookToWishlist.add(user_id=42, book_id=101)` сохраняет связь в `wishlists` (таблица PostgreSQL) и коммитит транзакцию. Затем роутер публикует `WISHLIST_ADD`. Покупатель получает `201 Created` и видит книгу в избранном. [Карточка книги](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/product/api/routers/book.py#L112) · [Добавление в избранное](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/order/api/routers/wishlist.py#L73).

### 2. RabbitMQ передаёт события, обработчик записывает историю

Роутеры витрины вызывают `publish_user_personal_books_reco_rmq_safe(routing_key=..., event=event, correlation_id="42")`. Для этого сценария ключи маршрутизации имеют значения `events.search`, `events.view` и `events.wishlist_add`. Через aio-pika продюсер сериализует модель методом `model_dump_json()` и вызывает `exchange.publish(message, routing_key=...)`. У сообщения режим `PERSISTENT`, а `user_events` (durable topic exchange RabbitMQ) маршрутизирует его в `personal_book_reco` (durable очередь RabbitMQ) по маске `events.#`. Роутер ждёт попытку публикации. При исключении безопасная обёртка пишет ошибку в лог, а ответ поиска, карточки или избранного сохраняется. Например, книга может уже появиться в избранном, пока профиль остаётся без сигнала о добавлении. [Продюсер](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/user/service/infrastructure/rabbitmq/producer/reco_events.py#L12) · [Публикация через aio-pika](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/shared/service/infrastructure/rabbitmq/producer.py#L15).

Процесс `recommendation_consumer` подписывается через `queue.consume(_process_message)` с `prefetch_count=10`, валидирует тело методом `CustomerPersonalRecoEVENT.model_validate_json(message.body)` и через Dishka получает `BookPersonalRecoForCustomerUC`. Контекст `message.process(requeue=False)` подтверждает успешную обработку. При проброшенном исключении сообщение отклоняется без возврата в исходную очередь и через `user_events_dlx` (fanout exchange RabbitMQ) уходит в `personal_book_reco_dlq` (durable очередь RabbitMQ для отклонённых сообщений). [Consumer и маршрутизация ошибок](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/product/service/infrastructure/rabbitmq/book/consumers/personal_reco.py#L24).

В `generate(event)` первый просмотр №101 создаёт `event_dedup:42:101:view` (строка Redis со значением `1`) командой `SET` с `NX` и `EX=60`. Второй просмотр, обработанный в эти 60 секунд, видит уже существующий ключ и заканчивается до записи события. Поэтому одно обновление страницы не удваивает интерес к книге. Правило применяется к `VIEW` с `book_id`, отсчёт начинается при обработке. Если запись в PostgreSQL падает после установки ключа, ключ может пережить ошибку до истечения TTL.

В транзакции SQLAlchemy обработчик читает `get_category_and_author_id_by_book_id(book_id=101)` и записывает `CustomerEventModel` (ORM-модель) в `user_events` (таблица PostgreSQL). В сохранённом просмотре `event_type=VIEW`, `category_id=7`, `author_id=11`, `weight=0.5`, `metada={}` (`dict` в Python, колонка JSON, имя поля именно `metada`). Запись избранного сохраняет те же ID с весом `1.5`. У поиска вес `0.3`, поле `metada` содержит фразу и размер страницы, а три ID книги, категории и автора равны `NULL`. Так профиль может считать интересы по журналу с уже сохранёнными ID. [Сохранение и дедупликация](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/product/service/usecase/book/personal_reco.py#L38) · [Модель журнала и веса](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/user/db/postgres/models.py#L107).

### 3. Обработчик инвалидирует кеш и ставит один пересчёт на серию действий

После коммита каждого сохранённого события `invalidate(user_id=42)` удаляет `user_reco_profile:42` (строка Redis с JSON-объектом профиля) и `user_reco_vector:42` (строка Redis с JSON-массивом чисел). `_update_user_reco_profile(user_id=42)` делает `INCR` для `user_reco:42:version` (целочисленный счётчик в строке Redis) и выставляет TTL 30 дней. Для `user_reco:42:pending` (строка Redis со значением `1`) использует `SET NX EX 120`. Ошибки инвалидации и постановки логируются отдельно от транзакции. Уже сохранённое событие остаётся в PostgreSQL.

Первое событие создаёт флаг. `CustomerTaskiqSchedulesPublisher.update_user_reco_profile(user_id=42)` вызывает `update_user_reco_books_profile_schedule.kicker().with_labels(delay=30).kiq(42)`. Taskiq использует `AioPikaBroker(delayed_message_exchange_plugin=True)` поверх RabbitMQ. Следующие сохранённые события обновляют TTL флага до 120 секунд без создания ещё одной задачи и без переноса уже запланированного запуска. В примере за исходные 30 секунд успевают записаться поиск, первый просмотр и избранное. Версия становится `3`. Так за три действия подряд Ollama обычно вызывается один раз. [Версия и флаг](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/product/service/usecase/book/personal_reco.py#L217) · [Постановка задачи](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/user/service/infrastructure/taskiq/schedules/customer/base.py#L12).

### 4. Воркер собирает интересы и вычисляет эмбеддинг

Taskiq-воркер вызывает `CustomerPersonalBooksRecoProfile.build(user_id=42)`. Он захватывает `user_reco:42:lock` (строка Redis, `SET NX EX 600`), проверяет флаг `pending` и запоминает `start_version=3`. Второй воркер по тому же пользователю завершится, если блокировка занята. При отсутствии `pending` пересчёт тоже пропускается. TTL освобождает ключ при зависании, а штатный путь удаляет его в `finally`. У задачи включены повторы при исключении с `max_retries=3`. [Задача Taskiq](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/user/service/infrastructure/taskiq/schedules/customer/update_customer_recs_vector.py#L5) · [Блокировка и ход пересчёта](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/user/service/infrastructure/customer/reco_profile.py#L522).

**Профиль.** `get(user_id=42)` читает кеш. При промахе `get_list_by_user_id_by_new(user_id=42)` выбирает до 200 последних событий по `created_at DESC`. В `category_scores` и `author_scores` (словари Python) суммируется `event.weight × exp(−age_days / 30)`, где возраст — число полных суток по UTC. Например, сигнал веса `1.5` спустя 30 суток даёт около `0.55`. В `CustomerRecoProfileDTO` (dataclass) попадают до пяти ID категорий и пяти ID авторов по сумме баллов, до десяти уникальных запросов от новых к старым, уникальные ID книг с любым взаимодействием и отдельно ID книг с `PURCHASE` в этом срезе. На первом пересчёте поля имеют значения `top_categories=[7]`, `top_authors=[11]`, `recent_searches=["Письма"]`, `interacted_books=[101]`, `purchased_books=[]`. Оба балла равны `2.0` в день события. Поиск без ID книги меняет текст профиля, а счётчики категории и автора остаются прежними. Профиль кешируется на 3600 секунд. [Агрегация профиля](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/user/service/infrastructure/customer/reco_profile.py#L251).

При чтении профиля сервис берёт вектор из Redis. Если ключа нет, делает `CustomerRecoProfileQdrantREPO.get(point_ids=[42], with_vectors=True)`, который вызывает `AsyncQdrantClient.retrieve` в `user_reco_profile` (коллекция Qdrant). Найденный вектор прогревает Redis на 3600 секунд. Поэтому после инвалидации и до отложенной задачи запрос может взять свежие интересы и последний сохранённый вектор. Если точки пользователя ещё нет, вектор остаётся `None`. [Чтение вектора](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/user/service/infrastructure/customer/reco_profile.py#L335).

**Вектор книг и текст интересов.** `_update_profile(user_id=42)` берёт первые 50 ID из `interacted_books` и вызывает `BooksQdrantREPO.get(point_ids=[101], with_vectors=True)`. В `books` (коллекция Qdrant) ID точки равен ID книги, а `payload` (словарь метаданных точки Qdrant) содержит, среди прочего, `category_id` и `author_id`. Обе коллекции настроены на 1024 измерения и косинусную близость. При индексации `BooksEmbeddingTextBuilder.execute(book)` собирает заголовок, автора, категорию, год при наличии и до 1000 символов описания. `OllamaEmbedder.embed_batch(texts)` отправляет через HTTPX `POST /api/embed` с `{"model":"bge-m3","input":texts}`, а индексатор сохраняет полученные векторы через `upsert(wait=True)`. Постановка задачи индексации при старте и периодическая сверка с PostgreSQL поддерживают книжные точки для этого запроса. [Построение книжных точек](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/product/db/qdrant/collections/books.py#L28) · [Ollama API](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/shared/service/infrastructure/ollama/embedder.py#L14).

Воркер вызывает `get_weights_by_book(user_id=42, book_ids=[101])`. PostgreSQL суммирует сохранённые веса по книгам без затухания по возрасту и без лимита 200 на строки в этом запросе. Сумма ограничивается диапазоном `[0.1, 3.0]`, а при отсутствии суммы используется `0.1`. Книга №101 получает вес `2.0`. NumPy вычисляет `np.average(vectors_np, axis=0, weights=weights_np)` на массивах `float32`. Без взаимодействий с книгами или без найденных книжных векторов метод завершится до вызова Ollama. Поэтому одних поисковых фраз для создания первого вектора недостаточно.

Для текстовой части воркер получает имена авторов через `get_by_ids(author_ids=[11])`, названия категорий через `get_by_ids(category_ids=[7])` и до пяти описаний через `get_descriptions_by_ids(book_ids=[101], limit=5)`. Каждое описание обрезается до 300 символов. `CustomerRecoProfileEmbeddingTextBuilder.execute(profile)` добавляет фразу «Письма» и собирает строку из непустых частей «Авторы», «Категории», «Поиски», «Темы книг». `OllamaEmbedder.embed(text)` передаёт `input=[text]` и возвращает первый эмбеддинг ответа. Воркер складывает `0.7 × средний вектор книг + 0.3 × вектор текста`, делит сумму на её L2-норму при ненулевой норме и преобразует результат в `list[float]`. Сначала записывает его в Redis, затем делает `save(QdrantPointDTO(id=42, vector=..., payload={"top_categories":[7],"top_authors":[11]}))` с `upsert(wait=True)` в Qdrant. Redis сразу обслуживает ленту, а Qdrant хранит точку для поиска похожих профилей. [Расчёт и запись вектора](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/user/service/infrastructure/customer/reco_profile.py#L366).

### 5. Версия подхватывает действие, пришедшее во время расчёта

Около 32-й секунды, когда первая задача уже прочитала данные для расчёта, покупатель открывает книгу №102. Consumer сохраняет новый `VIEW` с весом `0.5`, удаляет кеши и увеличивает версию до `4`. Первая задача дописывает рассчитанный вектор и считывает `end_version=4`. Затем она удаляет прежний `pending`. Из-за `4 != 3` метод `_rebuild(start_version=3, end_version=4, user_id=42)` создаёт флаг через `SET NX` и при успехе ставит следующую задачу с задержкой 30 секунд.

Следующий воркер видит обе книги. В книжном среднем веса равны `2.0` для №101 и `0.5` для №102, в профиле теперь `top_categories=[7, 9]` и `top_authors=[11, 12]`. Задача обновляет Redis и точку пользователя в Qdrant, удаляет `pending` и освобождает блокировку. Версия нужна, чтобы событие, записанное после чтения истории первой задачей, попало в следующий результат. Сравнение версий следует за записью вектора, поэтому первый снимок может быть доступен до публикации второго. [Повторная постановка](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/user/service/infrastructure/customer/reco_profile.py#L489).

### 6. Планировщик добавляет дневную статистику популярности

Допустим, за те же сутки UTC по книге №101 появились две строки в `order_items` (таблица PostgreSQL) с `quantity=3` и `quantity=1`, одно добавление в `wishlists`, один отзыв в `reviews` (таблица PostgreSQL) и один уникальный зритель. К моменту расчёта средний рейтинг `books.rating` равен `4.5`. В `00:10 UTC` (`03:10 МСК`) Taskiq Scheduler считывает метку `schedule=[{"cron":"10 0 * * *"}]` задачи `update_books_popularity()` и отправляет её воркеру. Воркер определяет границы вчерашних суток как `[yesterday_start, today_start)` по UTC. [Ежедневная задача](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/product/service/infrastructure/taskiq/tasks/book/update_popular_books.py#L38).

| Сигнал за вчерашние сутки | Что считает SQLAlchemy в PostgreSQL | Вклад для №101 |
|---|---|---:|
| Позиции заказов | `COUNT(1)` по `order_items.created_at` и `book_id`. В запросе отсутствуют условие по статусу заказа и суммирование `quantity` | `2 × 0.60 = 1.20` |
| Добавления в избранное | Количество сохранившихся строк `wishlists` с `created_at` в интервале | `1 × 0.30 = 0.30` |
| Отзывы | Количество строк `reviews` с `created_at` в интервале | `1 × 0.05 = 0.05` |
| Рейтинг | Текущий `books.rating` на момент расчёта | `4.5 × 0.05 = 0.225` |
| Уникальные просмотры | `COUNT(DISTINCT user_id)` по событиям `VIEW` в `user_events` за интервал | `1 × 0.10 = 0.10` |

Подзапросы группируются по `book_id` и присоединяются через `LEFT OUTER JOIN`. `COALESCE(..., 0)` даёт ноль отсутствующим сигналам, поэтому, например, пустой рейтинг не обнуляет вклад продаж. В выборку входят доступные книги с хотя бы одной позицией заказа, добавлением, отзывом или просмотром за сутки. Для №101 получается `popularity_score=1.8750`. Уникальный зритель даёт единицу за сутки даже при нескольких сохранённых просмотрах, разнесённых больше чем на минуту.

Воркер читает SQL-результат через `session.stream(stmt).partitions(1000)` и пишет в `book_popularity_stats` (таблица PostgreSQL) поля `book_id`, `stat_date`, `sales`, `wishlist_adds`, `reviews` и `popularity_score`. Просмотры и рейтинг входят в score без отдельных колонок в этой таблице. PostgreSQL `INSERT … ON CONFLICT (book_id, stat_date) DO UPDATE` перезаписывает метрики совпавшей пары. После всех пачек идёт один `commit()`, при исключении — `rollback()`. Для чтения `popularity_window_subquery()` суммирует дневные баллы за семь календарных дней, заканчивая последней датой, фактически присутствующей в таблице. Это позволяет ленте использовать последний рассчитанный период при задержке следующего запуска. Тот же подзапрос используется в отдельном каталожном «Популярном». [Запись дневных итогов](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/product/service/infrastructure/taskiq/tasks/book/update_popular_books.py#L137) · [Окно чтения](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/product/db/postgres/repositories/sqlalchemy/book.py#L36).

### 8. Браузер получает карточки и продолжает с тем же курсором

`BookMainRecoBlender.mix(slots, seed=cursor.seed, page=cursor.page)` перемешивает 20 мест с помощью `Random(seed ^ page).shuffle(pattern)`. `slots` — `BookBlenderSlotsDTO` (dataclass с четырьмя списками ID). Для каждого места смешиватель берёт первый ещё не использованный ID из очереди нужного источника (`collections.deque`). Если очередь пуста, он пробует остальные в порядке «персональные → популярные → новинки → случайные». Например, если №310 есть в персональных и новинках, в итоговый список он попадёт один раз. Смешиватель использует уже собранные ID, поэтому при нехватке уникальных кандидатов страница может оказаться короче. [Смешивание источников](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/product/service/infrastructure/query_handlers/book/main_reco.py#L1116).

`BookSQLAlchemyREPO.get_preview_by_ids(book_ids=merged_ids)` загружает книги, категории и авторов из PostgreSQL. Обработчик восстанавливает порядок смешивателя и отдаёт `BooksMainRecoRESP` (Pydantic-модель) с полями `books` (массив JSON с карточками) и `next_cursor` (строка или `null`). В интерфейсе появляются карточки с названиями, авторами и ценами. Если итоговых ID нет или по ним не нашлось ни одной карточки, сервер возвращает `books=[]` и `next_cursor=null`. [Загрузка карточек](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/product/db/postgres/repositories/sqlalchemy/book.py#L412) · [Формирование ответа](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/product/service/infrastructure/query_handlers/book/main_reco.py#L1301).

До ответа сервис пишет `merged_ids` (список Python с итоговыми ID) в два ключа. `book_reco:seen:{session_id}` (список Redis) через `RPUSH`, `LTRIM` и `EXPIRE` удерживает последние 400 записей на 30 минут после последней записи. Следующая страница читает их через `LRANGE` и исключает из своих кандидатов. Сам `RPUSH` атомарен, поэтому одновременные записи не затирают друг друга. Два параллельных запроса всё же могут прочитать одинаковый предыдущий список и выбрать пересекающиеся книги. Браузерный пейджер блокирует второй запрос, пока первый выполняется.

`book_reco:impressions:42` (список Redis) теми же командами удерживает последние 300 записей на трое суток после последней записи. Эта память переживает открытие новой сессии. Штраф `×0.25` действует в векторной, коллаборативной и холодной персональной выдаче, а также в новинках. Популярный и случайный источники в этом запросе используют общие исключения текущей сессии. История фиксирует серверную выдачу, поэтому долистывание до карточки для учёта показа не требуется. [Память показов](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/product/service/infrastructure/query_handlers/book/main_reco.py#L117).

### 9. При дальнейшем листании включается коллаборативный подбор

Допустим, покупатель получил 25 страниц в векторном режиме и курсор накопил `personalized_offset=200` (по 8 за вызов). Это счётчик объёма выдачи, который переключает стратегию. Обычный векторный запрос его как SQL offset или Qdrant offset не использует. Переключение также срабатывает раньше при ответе Qdrant меньше `limit=8` точек. С курсором в режиме `collaborative` запрос продолжает этот подбор, пока у покупателя есть вектор.

`find_similar_users(vector=profile.vector, limit=50, exclude_id=42)` вызывает `query_points` в `user_reco_profile` и исключает собственную точку. Пусть у соседа со score `0.9` список категорий `[7, 15]`, а у соседа со score `0.6` — `[15, 7]`. Вклад категории равен `score / (rank + 1)`, где ранг начинается с нуля. Баллы категории 7 и 15 составят `1.20` и `1.05` соответственно. Обработчик сортирует категории, берёт первый блок до десяти, затем переключает блок каждые три коллаборативные страницы по `collaborative_offset // limit`. Если новый блок пуст, снова берёт первый.

Затем `recommendations_for_user_profile(vector=profile.vector, limit=80, exclude_ids=..., category_ids=[7, 15])` передаёт `MatchAny` по `category_id` в книжную коллекцию. Соседи определяют категории, а близость книг считается по вектору самого покупателя. Поэтому покупатель может увидеть книгу из соседской категории 15, сохранив тематическую близость к собственной истории. Результат — до восьми взвешенно выбранных ID с учётом недавних показов, режим `collaborative` и увеличение `collaborative_offset` на 8. При отсутствии похожих пользователей или категорий источник возвращает пустой список и смешиватель использует доступные ID остальных источников. [Поиск соседей](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/user/db/qdrant/repositories/customer/reco_profile.py#L28) · [Расчёт категорий и поиск книг](https://github.com/luciuseneca/fastapi-bookshop/blob/e281be01f267ee0a3215f61e1cf6312b33434ba6/app/product/service/infrastructure/query_handlers/book/main_reco.py#L827).

## Другие случаи

### 1. Новый покупатель и проверка событий или дневного расчёта

Покупатель №77 сразу после входа запрашивает первую страницу. Истории и точки пользователя в Qdrant ещё нет. `BookColdCandidatesProvider.get()` читает `book_reco:cold_candidates:v2` (общая строка Redis с JSON-массивом). При промахе SQL объединяет до 200 доступных книг по `total_sales DESC, random_key ASC` и до 100 книг по `id DESC`, удаляет дубли и кеширует пул на 600 секунд. Случайный ключ разрешает ничьи по продажам, поэтому при нулевых продажах верхняя часть пула может охватывать разные части каталога.

Скоринг пула использует сглаженный рейтинг `(10 × средний рейтинг оценивавшихся книг пула + rating × sum_ratings) / (10 + sum_ratings)`, `log1p(total_sales)` и относительное место ID в пуле. В формуле взят именно `sum_ratings` (сумма выставленных баллов в ORM-модели). Счётчик оценок в модели называется `total_ratings`. Рейтинг и продажи нормируются по максимумам пула, новизна — по рангу. Для персонального холодного старта вес равен `0.10 + 0.60 × quality + 0.20 × sales + 0.10 × freshness`. Для резервного «Популярного» без дневной статистики — `0.10 + 0.25 × quality + 0.55 × sales + 0.10 × freshness`. Минимум `0.10` сохраняет шанс у старых книг при нулевых рейтингах и продажах. Взвешенная выборка сначала соблюдает максимум две книги категории и две автора и ослабляет лимиты при нехватке. У №77 при наполненном каталоге появляются карточки уже на первой странице. ### 2. Qdrant падает во время поиска книг

Покупатель №42 передаёт действительный курсор, его вектор доступен в Redis, а `query_points` книжной коллекции завершается исключением. `gather` даёт остальным источникам закончить. Обработчик логирует сбой и заменяет персональный результат на пустой список с прежним режимом и смещениями. Если популярное дало шесть ID, новинки четыре и случайный источник два, итог составит до 12 карточек. При следующем запросе персональная ветвь сможет повторить попытку с прежним режимом и смещениями. Отмена всего запроса через `CancelledError` пробрасывается. Сбой чтения профиля до `gather` или загрузки карточек после смешивания этим механизмом не перехватывается.
