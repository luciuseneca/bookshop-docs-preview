# Персональные рекомендации

После входа покупатель видит на главной блок **«Рекомендации для вас»** с подгрузкой при прокрутке. На страницу отводится **20 слотов** — 8 для персональных книг, 6 для популярных, 4 для новинок и 2 для случайных находок. Новый покупатель сразу получает подборку из каталога. Когда появляются интересы к категориям, лента учитывает их ещё до готовности вектора. С вектором работает поиск похожих книг, а при нехватке кандидатов подключаются категории похожих покупателей. Гость видит отдельный блок «Популярное». Для проверки есть тестовый приём событий и ручной запуск пересчёта популярности.

## От первого поиска до персональной страницы

1. **Покупатель ищет «Шерлок Холмс» по названию в категории «Детективы», дважды за минуту открывает книгу №42 и кладёт её в корзину.** Поиск и карточка возвращают обычный результат, корзина обновляется. При обработке каждого действия API пытается опубликовать JSON-событие в RabbitMQ, откуда оно попадает в `personal_book_reco` (очередь RabbitMQ). Поиск по названию или имени автора внутри категории фиксируется только на первой странице, даже при нуле результатов. Сохраняются фраза и число результатов на странице. Сбой публикации логируется, основное действие завершается своим обычным ответом.
2. **Воркер сохраняет сигналы.** Он валидирует сообщение, подставляет категорию и автора по ID книги и записывает событие с весом в `user_events` (таблицу PostgreSQL). Для просмотра `SET NX` создаёт ключ Redis на 60 секунд для пары «покупатель, книга». Второй просмотр отбрасывается, поэтому категория и автор получают **+2,5** за просмотр и корзину. Поиск даёт фразу для вектора, поскольку штатное событие поиска приходит без ID книги и без категории. Ошибка обработки отправляет сообщение в `personal_book_reco_dlq` (очередь RabbitMQ для проблемных сообщений) без автоматической повторной доставки.
3. **Следующий запрос ленты уже может учесть детективы.** После записи воркер удаляет из Redis профиль (JSON-объект) и вектор (JSON-массив). Для них используются отдельные ключи с TTL в один час. При промахе профиль собирается из **200 последних событий**, а вектор читается из `user_reco_profile` (коллекции Qdrant). Для топ-5 категорий и топ-5 авторов веса складываются с затуханием `exp(−возраст_в_днях / 30)`. Профиль также хранит до 10 уникальных поисковых фраз и ID книг, с которыми покупатель взаимодействовал, отдельно отмечая покупки по событиям `purchase` (типу события). Пока фоновая задача ждёт, свежий профиль может работать с прежним вектором или с подбором по категориям, если вектора ещё нет.
4. **В фоне Taskiq обновляет вектор.** После сохранения события воркер увеличивает счётчик версии в Redis. Первый флаг `pending` (ключ Redis) ставит задачу через RabbitMQ с задержкой **30 секунд**. Следующие события продлевают TTL флага до **120 секунд**, сохраняя исходное время запуска. Воркер берёт блокировку через `SET NX` на **10 минут**, проверяет флаг и сравнивает версии до и после расчёта. Он снимает флаг и планирует новый запуск, если версия изменилась. Блокировка снимается в `finally`. Если событие попадает между финальным чтением версии и удалением флага, его пересчёт может отложиться до следующего события.
5. **Следующая выдача может использовать новый вектор.** Воркер берёт эмбеддинги до 50 последних уникальных затронутых книг из `books` (коллекции Qdrant). Для каждой книги он суммирует веса всех её событий у покупателя и ограничивает результат диапазоном 0,1–3. Эти векторы заранее рассчитаны по названию, автору, категории, году издания и описанию. Из взвешенного среднего векторов книг берётся **70%**, из вектора текста профиля — **30%**. Ollama с моделью `bge-m3` кодирует в текстовом векторе авторов, категории, поисковые фразы и до пяти фрагментов описаний. Итог нормализуется и сохраняется в Redis и Qdrant. Если покупатель только искал и ещё ни с одной книгой не взаимодействовал, первого вектора пока не будет.

| Событие | Вес |
| --- | ---: |
| Просмотр / поиск | +0,5 / +0,3 |
| Добавление в избранное / удаление из него | +1,5 / −0,5 |
| Добавление в корзину / удаление из неё | +2 / −0,3 |
| Покупка / поделиться / предпросмотр | +3 / +1,2 / +0,8 |
| Оценка в отзыве | `(оценка − 3) × 0,75`, например 1 → −1,5, 5 → +1,5 |

Покупка, удаление из корзины, отправка ссылки и предпросмотр поддерживаются как тестовые сигналы. Штатные маршруты их не публикуют. Например, покупатель может отправить `{"type":"rating","book_id":42,"metadata":{"rating":5}}` (JSON-объект) в тестовый `POST /api/books/events/fdkhefkewqf/fdwowehfkwef/fwlkehfkwe`. Сервер берёт ID покупателя из токена и возвращает `202` после публикации. Воркер затем запишет событие с весом +1,5, а реальный отзыв при этом не создаётся.

## Как собирается и листается лента

| Слоты | Как выбираются книги |
| --- | --- |
| **8 персональных, без вектора** | Если категории известны, PostgreSQL выбирает кандидатов внутри них по рейтингу и продажам. Если категорий ещё нет, используется общий пул из топ-200 по продажам и 100 новинок, кешируемый в Redis на 10 минут. Вес учитывает продажи, новизну и рейтинг, сглаженный к среднему по пулу. Так одна пятёрка влияет слабее. |
| **8 персональных, с вектором** | Qdrant ищет до 80 книг по косинусной близости. Для кандидата из топ-3 категорий множитель веса растёт на 0,15, из топ-3 авторов — ещё на 0,10. При взвешенной выборке стараются взять не больше двух книг на категорию и автора. Если иначе слоты пустуют, ограничение снимается. |
| **8 персональных, коллаборативный режим** | Включается, если Qdrant вернул меньше восьми книг или счётчик векторной выдачи достиг 200. Он растёт на восемь за страницу и служит порогом переключения режима. Qdrant находит до 50 похожих профилей, кроме текущего. Балл категории складывается из вкладов `сходство / место категории в профиле`. Например, вторая категория соседа со сходством 0,8 получает +0,4. Каждые три страницы выбирается следующая группа из 10 категорий. Внутри группы книги ищутся по вектору самого покупателя. Без похожих профилей персональные слоты остаются без кандидатов. |
| **6 популярных** | Взвешенная выборка по сумме дневных баллов за семь дней, включая последнюю дату со статистикой. Если начальный запрос не находит статистику, используется общий пул холодного старта с повышенным весом продаж. |
| **4 новинки** | PostgreSQL выбирает книги по убыванию ID, при наличии интересов — внутри топ-категорий. Свежие позиции получают больший вес. Лимит в две книги на категорию снимается, если иначе слоты пустуют. |
| **2 находки** | PostgreSQL идёт от случайной для сессии точки по `random_key` (индексируемому целочисленному полю книги). Если дальше книг нет, поиск начинается с начала диапазона. |

**Первая страница.** Браузер вызывает `GET /api/books/main/recommendations` без курсора. Сервер создаёт сессию, запускает четыре источника параллельно и перемешивает слоты по случайному зерну сессии и номеру страницы. Книги с событием покупки исключаются из персонального источника. При ошибке отдельного источника его список считается пустым, его позиция сохраняется, а свободные слоты берут оставшихся уникальных кандидатов других источников. Например, при сбое поиска книг в Qdrant и полном наборе остальных источников получится максимум **12 карточек**. Сбой при загрузке самого профиля может прервать запрос до запуска источников. Сервер загружает карточки из PostgreSQL и восстанавливает порядок по собранным ID. Доступность в векторной ветке зависит от актуальности индекса Qdrant, который сверяется с каталогом каждые 15 минут.

**Прокрутка и повторное открытие.** Ответ содержит `books` (JSON-массив карточек) и `next_cursor` (строку курсора или `null`). При прокрутке браузер передаёт строку в `encoded_cursor`. Подпись HMAC защищает ID сессии, зерно, страницу и позиции источников. У популярных позиция задаётся парой «балл, ID», у новинок — ID, у находок — `random_key`. Неверная подпись даёт `400`, пустая выдача завершает листание. В Redis хранятся последние **400 ID сессии** (список, TTL 30 минут). Если книга №42 уже была на первой странице, следующий последовательный запрос её пропустит. Два параллельных запроса могут прочитать один и тот же список до записи показов и вернуть повторы. После истечения TTL подписанный курсор ещё принимается, а память сессии уже пуста. Отдельный список Redis хранит последние **300 показов покупателя** с TTL 3 дня. В новой сессии вес №42 в персональной подборке и новинках умножается на **0,25**, поэтому книга всё ещё может появиться. Запросы без курсора ограничены **15 новыми сессиями за 60 секунд** на покупателя, затем API возвращает `429`. Листание этот лимит не расходует.

## Как обновляется популярность

Taskiq в **00:10 UTC (03:10 МСК)** считает предыдущие сутки по UTC. Для доступной книги с активностью за день берутся строки `order_items` (таблицы позиций заказа в PostgreSQL) без проверки статуса заказа и без умножения на количество экземпляров, записи `wishlists` (таблицы избранного в PostgreSQL), отзывы из `reviews` (таблицы PostgreSQL), текущий рейтинг книги и уникальные зрители из `user_events`. Несколько просмотров одного покупателя за сутки считаются за одного зрителя.

**Пример.** Две позиции заказа, одно добавление в избранное, один отзыв, текущий рейтинг 4 и три уникальных зрителя дают `2 × 0,60 + 1 × 0,30 + 1 × 0,05 + 4 × 0,05 + 3 × 0,10 = 2,05`. Задача записывает результат в `book_popularity_stats` (таблицу PostgreSQL) по паре «книга, дата». Повторный запуск в те же сутки обновляет ту же строку. Балл участвует в следующей выдаче популярных книг, а администратор видит дневной результат в админке. Ручной `POST /api/books/update-books-popularity/23edded/dwefewfew/dqwfqwfwqf` ставит ту же задачу в очередь и отвечает `202`. У маршрута нет проверки авторизации.
