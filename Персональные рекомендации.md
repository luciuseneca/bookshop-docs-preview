# Персональные рекомендации

## Возможности

Авторизованный покупатель видит на главной ленту из персональных рекомендаций, популярных книг, новинок и случайных находок. Ленту можно прокручивать сразу после регистрации. Поиски, просмотры и другие действия постепенно меняют подборку. В пределах сессии лента исключает недавно выданные книги, а между сессиями снижает вес показанных книг в части источников.

## Сквозной сценарий (E2E)

Покупатель `user_id=7` впервые открывает главную, ищет «космос» по названию в категории `category_id=5`, открывает книгу `book_id=42` автора `author_id=12` и добавляет её в избранное. Затем он возвращается на главную после пересчёта профиля. Идентификаторы, оценки и результаты выборок в примере условные.

| Компонент | Роль в сценарии |
| --- | --- |
| `publish_user_personal_books_reco_rmq_safe`, `_process_message`, `BookPersonalRecoForCustomerUC` | Роутеры отправляют события в RabbitMQ (брокер сообщений). Воркер принимает их, взвешивает и сохраняет в PostgreSQL (реляционная БД). |
| `CustomerPersonalBooksRecoProfile`, `CustomerPersonalBooksRecoProfileCache`, `CustomerProfileUpdateProcess` | Собирают интересы из событий, кешируют профиль и вектор в Redis (хранилище ключей и значений), координируют фоновое обновление через Taskiq. |
| `BooksQdrantREPO`, `CustomerRecoProfileQdrantREPO` | Читают и ищут точки в Qdrant (векторная БД). Коллекция `books` хранит векторы книг, `user_reco_profile` — векторы и топы интересов покупателей. |
| `BooksMainRecommendationsQH`, `BookMainRecoBlender`, `BookMainRecoSeenSession` | Запускают источники, смешивают подборки, учитывают предыдущие показы и возвращают страницу с курсором. |
| `update_books_popularity` | Готовит дневные баллы популярности, которые используют лента и общий раздел «Популярное». |

1. **Главная показывает первую страницу покупателю без истории**

   `createCursorPager` вызывает `GET /api/books/main/recommendations` без `encoded_cursor`. `auth_client` проверяет роль покупателя и берёт `user.sub=7` из access-токена. `get_main_book_recommendations` вызывает `BooksMainRecommendationsQH.for_user(user_id=7, encoded_cursor=None)`.

   `BookMainRecoSeenSession.ensure_new_session_allowed(7)` делает `INCR` счётчика новых сессий в Redis и при первом запросе ставит TTL 60 секунд. Допустимо **15 новых сессий за окно**, следующая даёт HTTP 429. Обработчик создаёт `BookMainRecoCursorDTO` (dataclass) с `session_id` из UUID, 32-битным `seed`, `page=0`, режимом `vector` и нулевыми смещениями. Запрос с курсором продолжает сессию без этого счётчика.

   `CustomerPersonalBooksRecoProfile.get(user_id=7)` ищет профиль и вектор в Redis. При промахе профиль строится из PostgreSQL, а вектор читается через `CustomerRecoProfileQdrantREPO.get(point_ids=[7], with_vectors=True)` → `BaseQdrantREPO` → `AsyncQdrantClient.retrieve`. У нового покупателя история пуста. `BookPersonalizedReco.get(limit=8, …)` выбирает ветку по `profile.vector` (список `float` или `None`) и `profile.top_categories` (список ID).

   | Состояние | Как заполняются персональные слоты |
   | --- | --- |
   | Вектора и категорий пока нет | `_cold_start` вызывает `BookColdCandidatesProvider.get()`. Тот читает общий пул из Redis или через `DatabaseHelper.session_factory` собирает в PostgreSQL до 200 доступных книг по продажам и до 100 по убыванию `id`, объединяет по `id` и кеширует на 10 минут. Вес учитывает сглаженный рейтинг, `log1p(total_sales)` и позицию по новизне. При сглаживании вес среднего рейтинга пула равен 10, вес рейтинга книги берётся из `sum_ratings` (сумма её оценок). |
   | Категории уже есть, вектора ещё нет | `_cold_start_by_categories` через `DatabaseHelper` берёт до `3 × limit` доступных книг этих категорий по рейтингу, продажам и `random_key`. Из оставшихся после исключений выбирает с весом `1 / (rank + 1)`, где `rank` начинается с нуля. |
   | Вектор есть | `BookPersonalizedReco` ищет близкие книги и при исчерпании векторного режима переходит к категориям похожих покупателей. Обе ветки разобраны в шаге 5. |

   Остальные источники тоже участвуют в первой странице. Главная отображает секцию, когда приходят карточки. Допустим, в этой сессии сервер выдал книгу `87`.

2. **Поиск, просмотр и избранное отправляют события в RabbitMQ**

   Запрос первой страницы `GET /api/books/categories/{category_slug}/title` передаёт `filters.title="космос"`. После `CategoryBooksSearchQH.by_title(filters=filters, pagination=pagination)` роутер формирует `SEARCH` с `metadata={"query":"космос","results_count":4}` (JSON-объект), где `4` — `len(result.books)`. Поиск по автору берёт `filters.name`. При перелистывании событие пропускается, поскольку `pagination.encoded_cursor` уже задан.

   `detail_book_router` получает карточку через `BookDetailQH.get_book(book_slug)` и формирует `VIEW` с `book_id=book.id=42`. `add_item_to_wishlist_router` после `AddBookToWishlist.add(user_id=7, book_id=42)` формирует `WISHLIST_ADD`. Каждый роутер передаёт `CustomerPersonalRecoEVENT` (Pydantic-модель с `user_id`, `type`, `book_id`, `metadata`) и `correlation_id="7"` в `publish_user_personal_books_reco_rmq_safe`. Эта обёртка ждёт отправки и журналирует ошибки публикации, а роутер возвращает результат основного действия.

   `publish_user_personal_books_reco_rmq` вызывает общий `publish_rmq`, который сериализует модель в JSON и публикует постоянное сообщение в topic exchange `user_events`, например с `routing_key="events.view"`. Отдельный воркер читает очередь `personal_book_reco`, привязанную по `events.#`. `_process_message` валидирует `message.body` через `CustomerPersonalRecoEVENT.model_validate_json` и вызывает `BookPersonalRecoForCustomerUC.generate(event)`. При успехе сообщение подтверждается, при исключении отклоняется без повторной постановки и попадает через `user_events_dlx` в `personal_book_reco_dlq`.

   Для теста `handle_personalized_reco_event_router` принимает `BookPersonalRecoEVENT` (Pydantic-модель без `user_id`), подставляет ID из токена и вызывает тот же издатель напрямую. **HTTP 202** означает, что событие опубликовано. Покрытие типов и их веса определены в `CustomerEventENUM` и `USER_EVENT_WEIGHTS`.

3. **Воркер записывает сигналы и строит профиль интересов**

   Для `VIEW` метод `_is_duplicate_view` пытается создать `event_dedup:7:42:view` через Redis `SET NX` с TTL 60 секунд. Если покупатель обновит карточку через 10 секунд, ключ уже существует и `generate` завершится до записи. Для первого просмотра `_book_meta(event)` вызывает `BookSQLAlchemyREPO.get_category_and_author_id_by_book_id(book_id=42)` и получает `(5, 12)` из PostgreSQL. У поиска `book_id=None`, поэтому категория и автор в событии пусты, хотя поиск шёл внутри категории.

   | Тип | Откуда приходит в обычном сценарии | Вес |
   | --- | --- | --- |
   | `VIEW` | Открытие карточки авторизованным покупателем | `0.5` |
   | `SEARCH` | Первая страница поиска категории по названию или автору | `0.3` |
   | `WISHLIST_ADD` | Добавление в избранное | `1.5` |
   | `WISHLIST_DEL` | Удаление из избранного | `−0.5` |
   | `CART_ADD` | Добавление в корзину | `2.0` |
   | `CART_REMOVE` | Поддерживается схемой и обработчиком | `−0.3` |
   | `PURCHASE` | Поддерживается схемой и обработчиком | `3.0` |
   | `RATING` | Создание отзыва. `BookRatingEventMeta` принимает оценку 1–5 | `(rating − 3) × 0.75`, то есть `1.5` за пятёрку. При отсутствующей или нечитаемой оценке вес `0` |
   | `SHARE` | Поддерживается схемой и обработчиком | `1.2` |
   | `PREVIEW` | Поддерживается схемой и обработчиком | `0.8` |

   `_calculate_event_weight(event_type=event.type, meta=event.metadata, user_id=7)` вычисляет вес. `generate` передаёт `CustomerEventModel` (ORM-модель строки таблицы `user_events`) в `CustomerEventSQLAlchemyREPO.save` внутри `SQLAlchemyTransaction`. В строке остаются `user_id`, `book_id`, `event_type`, `category_id`, `author_id`, `weight` и `metada` (JSON-поле). После коммита `CustomerPersonalBooksRecoProfileCache.invalidate(7)` удаляет оба ключа кеша.

   При следующем `get(user_id=7)` метод `CustomerEventSQLAlchemyREPO.get_list_by_user_id_by_new(user_id=7)` читает **до 200 последних событий**, от новых к старым. Для каждой категории и автора профиль суммирует `weight × exp(−age_days / 30)`. У свежих `VIEW` и `WISHLIST_ADD` возраст 0 дней, поэтому `category_scores[5]` и `author_scores[12]` получат по `0.5 + 1.5 = 2.0`. Из словарей баллов берутся до пяти `top_categories` и `top_authors`. `recent_searches` (список строк) хранит до десяти уникальных запросов, здесь `["космос"]`. `interacted_books` и `purchased_books` (списки ID) собираются без дублей. Второй строится из `PURCHASE` и используется для исключений персонального источника. Поля `CustomerRecoProfileDTO` (dataclass) и `vector` кешируются отдельными ключами, каждый на час. Пока новый вектор строится, чтение из Qdrant может вернуть предыдущий.

4. **Taskiq откладывает пересчёт и сохраняет новый вектор**

   После каждой записи `_update_user_reco_profile(user_id=7)` увеличивает Redis-ключ `version` и задаёт ему TTL 30 дней. Первое событие создаёт флаг `pending` через `SET NX` на 120 секунд. `CustomerTaskiqSchedulesPublisher.update_user_reco_profile(user_id=7)` публикует задачу `update_user_reco_books_profile_schedule` с `delay=30` в брокер Taskiq на RabbitMQ. Следующие события увеличивают версию и продлевают TTL флага. В примере **три сохранённых события дают версию `3` и один запланированный пересчёт**.

   Задача вызывает `CustomerPersonalBooksRecoProfile.build(user_id=7)`. `CustomerProfileUpdateProcess` берёт Redis-блокировку пользователя через `SET NX` на 600 секунд, проверяет `pending` и читает `start_version=3`. `_update_profile(user_id=7)` строит вектор из двух частей.

   | Часть | Как получается |
   | --- | --- |
   | Векторы книг, `70%` | Из `interacted_books` берутся до 50 ID, здесь `[42]`. `BooksQdrantREPO.get(point_ids=[42], with_vectors=True)` через `BaseQdrantREPO` читает векторы. `CustomerEventSQLAlchemyREPO.get_weights_by_book(user_id=7, book_ids=[42])` суммирует веса всех событий по этим книгам в PostgreSQL. Для `42` получается `2.0`. Перед взвешенным средним каждый вес ограничивается диапазоном `0.1–3.0`. |
   | Текст интересов, `30%` | Репозитории `BookAuthorSQLAlchemyREPO`, `BookCategorySQLAlchemyREPO` и `BookSQLAlchemyREPO` читают из PostgreSQL имена авторов, названия категорий и до пяти описаний книг. `CustomerRecoProfileEmbeddingTextBuilder.execute` соединяет их с запросом «космос». Описания обрезаются до 300 символов. `OllamaEmbedder.embed` вызывает `POST /api/embed` с моделью `bge-m3` и получает эмбеддинг (числовой вектор длиной 1024). |

   При отсутствии векторов книг пересчёт заканчивается до вызова Ollama. Сами книжные векторы заранее готовит `BooksQdrantCollection` той же моделью из названия, автора, категории и, при наличии, года и описания. В нашем примере вектор книги `42` есть. Сервис складывает обе части, делит результат на его L2-норму, если она больше нуля, и обновляет Redis. Затем `CustomerRecoProfileQdrantREPO.save` через `BaseQdrantREPO` делает upsert точки `id=7` с вектором и `payload={"top_categories":[5],"top_authors":[12]}` (метаданные точки в виде словаря).

   В конце `build` читает `end_version` и снимает `pending`. При `end_version=3` работа завершена. Если во время расчёта пришло событие и версия успела стать `4`, `_rebuild` пытается заново поставить `pending` и планирует ещё одну задачу при успешной установке. Блокировка снимается в `finally`. При занятой блокировке второй воркер завершает вызов.

5. **Главная смешивает персональные книги с тремя другими подборками**

   Покупатель возвращается на главную. В новой сессии `for_user` передаёт четырём источникам курсор и `excluded_ids` (список ID, уже выданных в текущей сессии). Персональный источник и новинки также получают профиль и `impressed_ids` (множество ID недавних показов покупателю). Источники работают параллельно через `asyncio.gather`.

   | Источник и квота | Как выбираются книги и продвигается курсор |
   | --- | --- |
   | `BookPersonalizedReco` — 8 | `BooksQdrantREPO.recommendations_for_user_profile(vector=profile.vector, limit=80, exclude_ids=…)` через `BaseQdrantREPO.get_similar` вызывает `AsyncQdrantClient.query_points` в `books`. Qdrant фильтрует показанные в сессии и купленные из профиля книги и возвращает `ScoredPoint` (точки с косинусным баллом и метаданными). `_rerank` умножает балл на `1 + 0.15` для топ-3 категорий и добавляет к множителю `0.10` для топ-3 авторов. После выборки `personalized_offset` растёт на 8 и служит порогом смены режима. Каждый запрос Qdrant получает новый список исключений. |
   | `BookMainPopularReco` — 6 | Через `DatabaseHelper` читает до 60 доступных книг с положительным баллом из `popularity_window_subquery()`. Исключает выданные в сессии и выбирает пропорционально баллу. Следующая выборка идёт ниже сохранённой пары `(popular_last_score, popular_last_book_id)` по баллу, затем по `id`. Если первый запрос статистики пуст, берёт общий пул `BookColdCandidatesProvider` с повышенным весом продаж. |
   | `BookMainNewReco` — 4 | Через `DatabaseHelper` берёт до 12 доступных книг по убыванию `id`, ограничивает топ-категориями профиля, когда они есть, и удаляет уже выданные ID. Вес зависит от позиции в окне свежести. Минимальный выбранный `id` становится `new_last_id`, следующая выборка ищет меньшие ID. |
   | `BookMainExplorationReco` — 2 | Через `DatabaseHelper` читает доступные книги по возрастающему `random_key`, начиная со случайной 63-битной позиции, вычисленной из `seed`. Последний ключ переходит в `exploration_last_random_key`. Если после него выборка пуста, запрос идёт с начала диапазона с теми же исключениями. |

   Взвешенные выборки воспроизводятся по `seed ^ page`. `_weighted_sample` случайно выбирает кандидатов с учётом весов, удаляет дубликаты и при нехватке добирает из исходного списка. Для персонального источника и новинок вес недавно показанной книги умножается на **`0.25`**. У книги `87` из топ-категории и топ-автора балл `0.8` после `_rerank` даёт `1.0`, а предыдущий показ снижает её вес до `0.25`. Она остаётся кандидатом. У ещё не показанной книги `88` из категории `5` балл `0.76` даёт вес `0.874`. Допустим, выборка взяла `88`. Векторная и общая холодная выборки сначала ограничиваются двумя книгами на категорию и двумя на автора. Новинки сначала ограничиваются двумя на категорию. При нехватке кандидатов ограничения ослабляются.

   Если Qdrant вернул **меньше восьми** книжных точек, `personalized_offset` достиг `200` или курсор уже в режиме `collaborative`, срабатывает `_fallback_to_collaborative`. Допустим, на одной из следующих страниц осталось семь точек. `_collaborative` вызывает `CustomerRecoProfileQdrantREPO.find_similar_users(vector=profile.vector, limit=50, exclude_id=7)` → `AsyncQdrantClient.query_points` в `user_reco_profile`. Сервис суммирует по категориям `similar_user.score / (rank + 1)`. Например, второй интерес соседа со сходством `0.8` добавит категории `0.4`. Каждые три страницы этой ветки берётся следующий блок из десяти категорий. При исчерпании блоков снова берётся первый. `BooksQdrantREPO.recommendations_for_user_profile` получает те же `vector`, `limit=80`, исключения и теперь `category_ids` выбранного блока. Курсор запоминает `mode="collaborative"` и увеличивает `collaborative_offset` на 8.

   `BookMainRecoBlender.mix(slots, seed, page)` перемешивает шаблон **8 + 6 + 4 + 2** и строит очереди из `BookBlenderSlotsDTO` (dataclass со списками ID). Для каждого слота берёт первый ещё не использованный ID из его очереди. Если очередь исчерпана, пробует остальные источники в порядке `personalized → popular → new → exploration`. Если отдельный источник выбросил исключение, `for_user` подставляет пустой список и сохраняет позицию этого источника в курсоре. Оставшиеся очереди заполняют доступные слоты.

6. **Браузер показывает карточки и продолжает сессию по курсору**

   `BookSQLAlchemyREPO.get_preview_by_ids(book_ids=merged_ids)` читает книги с авторами и категориями из PostgreSQL. `for_user` восстанавливает порядок `merged_ids` (список отобранных ID), а `BooksMainRecoRESP.from_page` превращает записи в карточки `books` и добавляет `next_cursor` (строка или `null`). Покупатель видит книгу `88`, выбранную по обновлённому профилю. При последовательном листании её ID уже входит в исключения для следующей страницы.

   | Что запомнил сервер | Как это влияет на следующую выдачу |
   | --- | --- |
   | `book_reco:seen:{session_id}` (список Redis) | `BookMainRecoSeenSession.add` добавляет `merged_ids` через `RPUSH`, оставляет последние 400 и обновляет TTL до 30 минут. `get(session_id)` возвращает их при запросе следующей страницы. |
   | `book_reco:impressions:{user_id}` (список Redis) | `add_impressions` оставляет последние 300 выданных ID и обновляет TTL до трёх дней. `get_impressions(7)` возвращает их как множество для штрафа по весу, включая новую сессию. |
   | `next_cursor` (подписанная строка) | `BookMainRecoCursorDTO.encode()` кодирует JSON с `session_id`, `seed`, `page+1`, режимом и позициями источников в URL-safe Base64 и подписывает HMAC-SHA256. `decode()` проверяет подпись и поля, при невалидном курсоре возвращается HTTP 400. |

   Когда нижний маркер списка входит в область прокрутки, `createCursorPager` отправляет `next_cursor` как `encoded_cursor` и дописывает карточки. Пустая выдача завершает листание.

7. **На следующий день просмотры влияют на общий балл популярности**

   В **00:10 UTC** Taskiq по расписанию запускает `update_books_popularity()`. Задача через `db_helper.session_factory()` группирует данные PostgreSQL по `book_id` за предыдущие сутки UTC. Если книгу `42` за этот день открывали покупатели `7` и `8`, она получает два уникальных просмотра. Учитываются доступные книги хотя бы с одним из четырёх дневных сигналов активности.

   | Сигнал | Как считается | Коэффициент |
   | --- | --- | --- |
   | Позиции заказов | Число строк `OrderItemModel` по `created_at` за сутки | `0.60` |
   | Добавления в избранное | Число оставшихся строк `WishlistModel`, созданных за сутки | `0.30` |
   | Отзывы | Число строк `ReviewModel`, созданных за сутки | `0.05` |
   | Рейтинг | Текущее значение `BookModel.rating`, `0` при `NULL` | `0.05` |
   | Просмотры | `COUNT(DISTINCT user_id)` по событиям `VIEW` за сутки | `0.10` |

   При одной позиции заказа, одном добавлении в избранное, одном отзыве, рейтинге `4` и двух зрителях `popularity_score` книги `42` за день равен **`0.60 + 0.30 + 0.05 + 0.20 + 0.20 = 1.35`**. Задача пишет строки `BookPopularityStatsModel` (таблица `book_popularity_stats` в PostgreSQL) пакетами до 1000, обновляя записи по ключу `(book_id, stat_date)`, и коммитит результат. Ручной POST-обработчик `run_update_books_popularity` ставит ту же задачу через `update_books_popularity.kiq()` и отвечает **HTTP 202** с `status="queued"`.

   При последующих запросах `popularity_window_subquery()` суммирует дневные баллы за семь дней от максимальной `stat_date` включительно. Поэтому новые `1.35` начинают влиять и на шесть популярных слотов персональной ленты, и на отдельный раздел «Популярное» после записи статистики.
