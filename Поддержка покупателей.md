# Поддержка покупателей

**WebSocket доставляет сообщения, PostgreSQL хранит историю, Redis Pub/Sub рассылает новые события, а RabbitMQ выносит генерацию ответа бота в отдельный процесс.** Пока обращение простое, бот отвечает по FAQ. После эскалации его подхватывает оператор.

## Подключение и история

Вкладка «Поддержка» открывает WebSocket `/api/support/ws` с access-токеном. Сервер проверяет JWT и роль покупателя, затем восстанавливает незакрытый чат или создаёт новый. Частичный уникальный индекс PostgreSQL допускает только один незакрытый чат на пользователя. Сервер кеширует данные активного чата в Redis на 5 минут.

При подключении клиент получает событие `history` со всеми сообщениями покупателя, включая закрытые чаты, в порядке создания и без пагинации. Для живого обмена сокет подписывается на канал текущего чата `schat:<chat_id>`. Каждое принятое сообщение сохраняется в PostgreSQL с типом отправителя (`user`, `bot`, `manager`), а время последнего сообщения обновляется. После фиксации транзакции `message` публикуется в Redis. Рассылку получают оба подключённых сокета. Покупатель видит своё сообщение после рассылки, а панель менеджера показывает отправленный текст сразу и пропускает его копию из Pub/Sub. Если сокет пропустил рассылку, переподключение восстанавливает сохранённые сообщения из БД.

## Антиспам и эскалация

- **Антиспам.** Redis считает попытки отправки по ID покупателя. Окно в 10 секунд начинается с первой попытки. Первые 5 сообщений проходят, каждое следующее в том же окне считается отдельным нарушением. Третье нарушение за 5 минут включает блокировку на 60 секунд и сбрасывает счётчик нарушений. Отклонённые сообщения не попадают в историю, а клиент получает событие `error` по открытому сокету.
- **Эскалация.** Проверка идёт в порядке приоритета. Сначала запрос оператора («оператора», «менеджер»), затем признаки сложного случая («оплата», «возврат», «заказ»), затем совпадение с заданным списком ненормативной лексики. Для первых двух групп регулярное выражение ищет совпадение с начала слова, поэтому учитываются склонения. При первом совпадении сервер сохраняет причину вместе с сообщением, а покупатель получает `system` о передаче оператору. Очередь панели показывает все открытые чаты без менеджера, включая чаты, где пока отвечает бот.
- **Отключение бота.** Новое задание на ответ отправляется, только пока у чата нет ни причины эскалации, ни назначенного менеджера. При изменении состояния кеш покупателя сбрасывается. Воркер не перепроверяет состояние чата, поэтому уже поставленный в очередь ответ может прийти после эскалации или закрытия.

## Как бот отвечает по FAQ

При запуске приложения задача Taskiq наполняет Qdrant. Модель Ollama `bge-m3` векторизует склеенные пары «вопрос + ответ», а стабильный ID из текста вопроса позволяет повторно загрузить те же записи без дублей.

Для обычного сообщения сервер после записи в БД отправляет `chat_id` и текст в `llm_queue` RabbitMQ. Воркер строит вектор вопроса через `bge-m3` и берёт из Qdrant до 5 записей FAQ с косинусной близостью от 0,5. Затем отправляет вопрос и найденный контекст в Ollama `llama3.1:8b` с просьбой отвечать только по этому контексту. Готовый ответ воркер сохраняет и публикует через тот же канал чата.

Пустая выдача или ошибка Qdrant приводит к готовой фразе «Я не могу подсказать Вам по вашему запросу». При ошибке генерации Ollama бот сохраняет сообщение об ошибке. Если не удалось получить сам вектор вопроса, воркер записывает ошибку в журнал и подтверждает задание RabbitMQ. В этом случае клиент остаётся без ответа, а исходное сообщение уже лежит в истории.

## Активность и завершение

- **Новое подключение.** Сервер публикует UUID новой сессии в отдельный канал покупателя. Предыдущий сокет, подписанный на этот канал, видит чужой UUID и отключается. При почти одновременных подключениях ещё не подписавшийся сокет может пропустить сигнал.
- **Простой.** Первое принятое сообщение покупателя или менеджера создаёт ключ активности в Redis на час. Дальнейшие сообщения от них продлевают TTL. Подключение и ответы бота его не обновляют. При уведомлении Redis об истечении ключа клиентский WebSocket закрывается, а чат остаётся открытым в PostgreSQL и восстанавливается при следующем подключении.
- **Закрытие чата.** Покупатель отправляет `{"action":"close"}`. Сервер выставляет `is_closed` и `closed_at`, сбрасывает кеш, рассылает `system` о закрытии и завершает сокет покупателя. Следующее подключение создаёт новый чат и снова загружает общую историю. Системные уведомления о передаче оператору, его назначении через WebSocket, уходе и закрытии рассылаются в момент события. История хранит сообщения участников.

**Пример.** Покупатель спрашивает «Сколько стоит доставка?». Воркер находит подходящую запись FAQ и отправляет ответ бота в чат. Следом покупатель пишет «Нужен оператор». Сервер сохраняет сообщение и причину `operator_request`, уведомляет покупателя о передаче и прекращает ставить новые задачи боту. Когда менеджер берёт чат из очереди, его ответ приходит по тому же WebSocket и остаётся в истории.
