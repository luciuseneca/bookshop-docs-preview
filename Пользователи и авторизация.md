# Пользователи и авторизация

Покупатель может зарегистрироваться по email, имени и паролю, затем активировать аккаунт кодом из письма. При следующих входах по паролю снова нужен код. Кнопка «Войти через Google» создаёт аккаунт по новому подтверждённому email или привязывает Google к существующему. После входа браузер может продлевать сессию, а API позволяет выйти на текущем устройстве или на всех сразу. У менеджеров поддержки и администраторов свои формы входа.

## Регистрация и вход по email

1. Анна вводит `anna@example.com`, имя `anna_books` и пароль `Books42!`. FastAPI приводит email к нижнему регистру и сохраняет в `users` (таблица PostgreSQL) покупателя с `is_active=False`. В базе лежит bcrypt-хеш со случайной солью. При входе `bcrypt.checkpw` сверяет введённый пароль с хешем.
2. Сервер генерирует шестизначный код через `secrets` и выдаёт браузеру `session_id` (UUID). `otp:<email>` (строка Redis с UUID) позволяет найти действующий код по адресу, а `otp:<session_id>` (строка Redis с JSON-объектом) хранит email, код, UUID и исходный TTL. Обе записи живут 5 минут в примерной конфигурации.
3. API публикует задачу Taskiq в RabbitMQ, после чего браузер показывает форму кода. Отдельный воркер отправляет письмо по SMTP. Если отправка падает, ошибка пишется в лог, а код остаётся в Redis до истечения TTL. Повторная выдача на тот же email в это время даёт `409`.
4. Анна вводит полученный код `042719`. Браузер отправляет UUID и код строкой, поэтому ведущий ноль сохраняется. Сервер находит запись в Redis, сравнивает код, активирует аккаунт в PostgreSQL и удаляет обе записи OTP. Анна сразу получает сессию и попадает на витрину. При следующем входе сервер сначала проверит, что покупатель активен и пароль верен, выдаст новый код, а при подтверждении ещё раз проверит активность и выдаст токены.

Если Анна введёт `042718`, получит `400` и сможет повторить ввод. После истечения кода или его успешного использования тот же UUID даст `400` с сообщением об истёкшем коде. Если регистрация осталась незавершённой, после истечения кода можно заново указать имя и пароль для той же записи. Повторная регистрация активного покупателя даёт `409`. Проверка наличия кода и запись в Redis разделены, поэтому два параллельных запроса могут успеть создать по коду.

## Вход через Google

Анна нажимает «Войти через Google». Authlib перенаправляет её в Google, а при возврате обменивает код авторизации на токены Google. Из `userinfo` (объект с данными профиля) приложение берёт имя, email и `sub` (идентификатор аккаунта Google). Неподтверждённый email отклоняется.

- **Новый email.** В `users` создаётся активный покупатель без пароля.
- **Тот же `anna@example.com`, провайдер ещё не привязан.** Сервер сохраняет `google` и полученный `sub` в полях `oauth_provider` и `oauth_id`. ID покупателя сохраняется вместе с его заказами. После привязки вход по паролю отклоняется.
- **Google уже привязан.** Если в базе хранится `oauth_id=g123`, то `sub=g123` разрешает вход, а `sub=g999` даёт `403` даже при совпадении email. Другой сохранённый провайдер даёт `409`.

На обратном запросе сервер создаёт refresh-сессию, ставит cookie и отправляет Анну на главную. Если в браузере нет access-токена, страница получает его через refresh. Привязка сохраняет прежнюю активность аккаунта, поэтому для незавершённой регистрации по email такой refresh будет отклонён.

## Что хранит браузер и как продлевается сессия

Access даёт доступ к API, refresh позволяет получить новую пару. Оба JWT подписываются приватным ключом RS256 и проверяются публичным. В обоих есть тип, ID пользователя (`sub`), уникальный ID токена (`jti`), время выдачи и срок действия. В access также есть роль. В примерной конфигурации access живёт 10 минут, refresh — 7 дней.

- **Access** приходит в JSON, хранится в `localStorage` (хранилище браузера) и уходит в API как `Authorization: Bearer …`. Витрина и панель поддержки используют разные ключи и принимают access своей роли. Refresh-cookie у них общая.
- **Refresh** хранится в cookie с `HttpOnly`, `SameSite=Strict` и путём `/api/users/`. Вместе с ней сервер выдаёт `csrf_token` (читаемая браузерная cookie). Для обеих cookie в коде задано `secure=False`. При обновлении и выходе JavaScript копирует CSRF-значение в `X-CSRF-Token`. Сервер сравнивает cookie и заголовок через `hmac.compare_digest`. Если значение отсутствует или отличается, запрос с валидным refresh получает `403`.

**Пример ротации.** При загрузке страницы без access браузер отправляет `R1` из cookie на `POST /api/users/token/refresh`. Сервер проверяет подпись, срок, тип и наличие сессии в Redis, затем читает аккаунт из PostgreSQL. Если аккаунт активен, удаляет сессию `R1`, сохраняет новую для `R2` и возвращает access с актуальной ролью. Браузер заменяет cookie и сохраняет access. Если аккаунт удалён или неактивен, сервер отзывает все его refresh-сессии и возвращает `403`.

После `401` браузер пробует обновить токен и при успехе повторяет исходный запрос один раз. Запросы одной страницы ждут одного общего обновления. Между вкладками такой координации нет, а проверка и замена сессии на сервере идут отдельными командами Redis. В текущем коде истёкший access даёт `403`, поэтому обычное истечение токена само по себе не запускает эту ветку автообновления.

## Лимит сессий, повтор токена и выход

`refresh:<jti>` (строка Redis с ID пользователя) живёт столько же, сколько выданный refresh. `user_refresh_sessions:<user_id>` (сортированное множество Redis) хранит `jti` по времени выдачи. При лимите 3 вход с четвёртого устройства вытесняет самую старую сессию по этому индексу. Ротация обновляет время выдачи. Истёкший ключ сессии может исчезнуть раньше своего элемента в индексе, поэтому счётчик иногда включает уже истёкшую сессию.

Если после обмена `R1 → R2` снова прислать ещё не просроченный `R1`, его ключа уже нет. Сервер считает это повторным использованием, отзывает все refresh-сессии пользователя, включая `R2`, и возвращает `401`. Такой же результат даст ещё действующий JWT вытесненной сессии. Просроченный refresh отклоняется при проверке JWT, до поиска сессии.

«Выйти» удаляет из Redis сессию по `jti` из cookie. `POST /api/users/logout/all` удаляет все refresh-сессии аккаунта. Уже выданный access на маршрутах с проверкой только JWT живёт до своего срока. При выходе браузер удаляет локальный access. Сервер формирует заголовки удаления cookie, но при выходе и ошибках ротации отправляет другой ответ без этих заголовков. Поэтому после обычного выхода главная может снова отправить оставшийся в cookie refresh и запустить отзыв остальных сессий по правилу повторного использования.

## Роли и подключение к чату

- **Покупатель.** С ролью `authorized_user` Анна открывает корзину, заказы, отзывы и клиентский чат.
- **Менеджер.** Олег вводит email и пароль в панели поддержки. Сервер проверяет роль, активность и bcrypt-хеш в `users`, затем выдаёт JWT с ролью `authorized_manager` без кода из письма. Олег видит список обращений. Защищённые HTTP-маршруты панели проверяют и роль в JWT, и текущую роль с активностью в базе.
- **Администратор.** Вводит email и пароль в SQLAdmin. После проверки панель хранит `admin_id` (поле отдельной сессии) и при обращении заново сверяет роль и активность в PostgreSQL. Выход из SQLAdmin очищает эту сессию.

Когда Анна открывает поддержку, браузер передаёт access в `?token=…` при подключении WebSocket. Клиент, который умеет задавать заголовки, может передать `Authorization: Bearer …`. Сервер проверяет подпись, срок, тип и роль до приёма соединения. По `sub` он находит или создаёт чат в `chats` (таблица PostgreSQL) и отправляет Анне историю из `chat_messages` (таблица PostgreSQL). Олег открывает чат из панели со своим токеном. Сервер проверяет роль менеджера и доступность назначения, а при первом назначении Анна видит сообщение, что Олег подключился. Токен покупателя на менеджерском канале отклоняется. Срок JWT проверяется при подключении, поэтому его истечение само по себе не закрывает открытый сокет.
