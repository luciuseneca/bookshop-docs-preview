# Пользователи и авторизация

## Возможности

- Покупатель регистрируется по email, имени пользователя и паролю. Код из письма активирует аккаунт и сразу открывает сессию. При следующем входе по паролю тоже нужен одноразовый код. Пока выданный код действует, повторный запрос возвращает ошибку.
- Через Google можно создать аккаунт, войти или привязать Google к существующему аккаунту покупателя по подтверждённому email. После привязки для входа используется Google.
- Сессии можно обновлять и завершать на текущем устройстве или на всех устройствах. У покупателей, менеджеров и администраторов разные точки входа и права.

## Сквозной сценарий (E2E)

Алиса регистрируется на компьютере, входит на телефоне с новым кодом, привязывает Google на планшете и затем завершает сессии. В примере `id=42`, коды и идентификаторы сессий условные. Сроки и лимит взяты из `.env.example`.

- `CustomerAuthenticationUC` принимает данные регистрации или входа, работает с `CustomerSQLAlchemyREPO` и передаёт `OtpAuthSession` выдачу кода. `send_otp_email` отправляет письмо через воркер Taskiq.
- `CustomerAuthorizationUC` подтверждает код и активирует нового покупателя. `CustomerGoogleAuthorizationUC` обрабатывает подтверждённый профиль Google. Оба используют `JWTGenerator` и `JWTRefreshAuthSession` для выпуска токенов и записи refresh-сессий.
- `JwtRefreshTokenUpdateUC` заменяет refresh-токен при обновлении access-токена. `CustomerLogoutUC` удаляет refresh-сессии. В браузере `apiFetch` подставляет access-токен и вызывает `refreshAccessToken` при `401`.

1. **Алиса отправляет форму регистрации.** Форма `/auth` вызывает `apiFetch` и отправляет `POST /api/users/register` с `email="Alice@example.com"`, `username="alice"`, `password="Bookshop!42"` (поля JSON-объекта). `CustomerRegisterREQT` (модель Pydantic) приводит email к нижнему регистру и проверяет длину локальной части до `@` (3–50), длину имени (3–20) и пароль (8–70 символов, заглавная и строчная латинские буквы, цифра и один из разрешённых спецсимволов).

   `register_user_router` вызывает `CustomerAuthenticationUC.register(user_data)`. Тот передаёт `email="alice@example.com"` в `CustomerSQLAlchemyREPO.get_by_email`. Репозиторий через `AsyncSession` ищет в PostgreSQL (реляционная БД) только покупателей, сравнивая email без учёта регистра. Записи пока нет. Если бы нашёлся **активный** покупатель, запрос завершился бы ошибкой `CustomerAlreadyExistsERR`. У **неактивного** покупателя без действующего кода можно обновить имя и хеш пароля.

2. **Сервер создаёт неактивный аккаунт и отправляет код.** Перед записью `register` вызывает `OtpAuthSession.get_by_owner(owner="alice@example.com")`. По email сервис через `RedisClient.string.get` ищет UUID сессии, затем запись самой сессии в Redis (хранилище ключей и значений). `is_otp_not_expired` проверяет наличие записи. **При действующем коде** сервер возвращает `409` (`OtpNotExpiredERR`). Алиса регистрируется впервые, поэтому проверка проходит.

   `user_hash_password(password)` вызывает `bcrypt.hashpw` со случайной солью из `bcrypt.gensalt`. `CustomerSQLAlchemyREPO.save` сохраняет `UserModel` (ORM-объект) с хешем, `role=CUSTOMER` и `is_active=False` через `AsyncSession.merge/flush`, а `SQLAlchemyTransaction.commit` фиксирует запись в `users` (таблица PostgreSQL).

   `generate_otp()` выбирает **шесть цифр** через `secrets.choice`, например `"038271"`. `OtpAuthSession.create(new_otp)` получает `OtpDTO` (датакласс) с `owner="alice@example.com"`, `code="038271"`, `session_id` (UUID v4, обозначим `S1`) и `ttl=settings.otp.ttl` (300 секунд). Сервис сохраняет через `RedisClient` две строки с одним TTL. Запись `otp:<email>` указывает на `S1` для проверки повторной выдачи, а `otp:<UUID>` содержит DTO в виде JSON для подтверждения введённого кода.

   `send_otp_email.kiq("alice@example.com", "038271")` ставит задачу в RabbitMQ (брокер сообщений). API отвечает **`201` с `session_id=S1`**, и форма показывает поле кода. В фоне воркер Taskiq берёт задачу, `send_otp_email` формирует письмо с кодом и сроком в минутах через `get_email_otp_body_conf`, а `send_letter_to_email` передаёт письмо SMTP-серверу.

3. **Алиса подтверждает код и активирует аккаунт.** Форма шлёт `POST /api/users/register/verify` с `session_id=S1` и `otp="038271"` (JSON-объект). `user_register_confirm_router` передаёт `CustomerAuthConfirmREQT` (модель Pydantic с UUID и строкой) в `CustomerAuthorizationUC.register_confirm`. Общий `_get_valid_otp(user_data)` читает запись через `OtpAuthSession.get(S1)` → `RedisClient.string.get` и сравнивает `otp.code` с `client_code="038271"` через `is_invalid_otp_code`. Строковый тип сохраняет ведущий ноль.

   | Результат проверки | Что происходит |
   |---|---|
   | Записи `S1` уже нет, например истёк TTL | `400`, `OtpExpiredERR`. |
   | Запись есть, код отличается | `400`, `OtpInvalidERR`. Сессия остаётся доступной до истечения TTL. |
   | Код совпал | `register_confirm` берёт email из `otp.owner`, повторно загружает покупателя через `CustomerSQLAlchemyREPO.get_by_email(email=otp.owner)` и требует неактивную запись. `user_make_active(user)` ставит `is_active=True` и обновляет `created_at`. Сервис сохраняет изменения, делает `commit` и вызывает `OtpAuthSession.delete(otp)`, который удаляет обе строки в Redis. |

4. **Сервер открывает сессию, браузер сохраняет токены.** `CustomerAuthorizationUC._jwt_tokens(user_id="42")` передаёт в `JWTGenerator.access_token` датакласс `JWTAccessTokenDTO(sub="42", role="authorized_user")`, а в `JWTGenerator.refresh_token` — `JWTRefreshTokenDTO(sub="42")` (датакласс). У каждого токена свой `jti` (UUID-строка), тип и отметки `iat`/`exp`. `jwt_encode` подписывает строки JWT приватным ключом (`RS256`). Access действует **10 минут**, refresh — **7 дней**.

   `_jwt_tokens` извлекает `jti` refresh через `jwt_decode` и вызывает `JWTRefreshAuthSession.create(user_id="42", jti=…, ttl=604800)`. `create` сохраняет сессию и обновляет список через `RedisClient`.

   | Запись | Для чего нужна |
   |---|---|
   | `refresh:<jti>` (строка Redis со значением `"42"`) | Проверка существования конкретной refresh-сессии. Ключ исчезает по TTL. |
   | `user_refresh_sessions:42` (упорядоченное множество Redis) | Список `jti` с временем создания в качестве оценки. На добавлении `ZCARD` сравнивается с `settings.auth.max_auth_user_sessions` (**3**). Перед добавлением четвёртой записи `ZRANGE 0 0` находит старейшую, а `remove(user_id, jti)` удаляет её ключ и элемент списка. TTL списка продлевается при добавлении, поэтому в нём могут оставаться `jti` с уже истёкшими отдельными ключами. |

   Роутер возвращает `access_token` в JSON, `setToken` сохраняет его в `localStorage` (браузерное хранилище ключей и значений), после чего форма открывает главную. `set_auth_cookies(response, jwt.refresh_token)` выставляет две cookie на срок refresh с `Secure=False` в конфигурации проекта.

   | Cookie | Как используется |
   |---|---|
   | `refresh_token` | `HttpOnly`, `SameSite=Strict`, `Path=/api/users/`. Браузер присылает её на refresh и logout. |
   | `csrf_token` | Случайное значение, доступное JavaScript, `SameSite=Lax`, `Path=/`. `csrfHeaders` копирует его в `X-CSRF-Token` для refresh и logout. |

5. **Алиса открывает корзину и чат поддержки.** `apiFetch` подставляет `Authorization: Bearer <access_token>`. Зависимость `auth_user` через `is_valid_jwt_access_token` → `jwt_decode` проверяет подпись публичным ключом, срок и тип `access_token`. Затем `require_roles` сверяет роль из токена.

   | Роль | Вход и проверка прав |
   |---|---|
   | Покупатель | `auth_client` требует `authorized_user`. Например, запрос корзины проходит с `sub=42` и передаёт ID покупателя обработчику. |
   | Менеджер | `ManagerLoginUC.execute(login_data)` ищет менеджера через `ManagerSQLAlchemyRepository.get_by_email`, проверяет активность и bcrypt-пароль и выдаёт пару токенов без OTP. `get_current_manager` проверяет `authorized_manager` через `auth_manager`, затем активность и роль по `sub` в PostgreSQL. |
   | Администратор | `AdminAuth.login` проверяет пароль, `is_active` и `UserRoleENUM.ADMIN` по записи в PostgreSQL, кладёт `admin_id` в `request.session` (словарь сессии SQLAdmin). На следующих запросах `AdminAuth.authenticate` снова проверяет активность и роль в базе. |

   Для WebSocket `auth_user_ws(websocket)` берёт access из Bearer-заголовка или из параметра `token`. Браузерный чат подключается к `/api/support/ws` со вторым вариантом. После проверки JWT обработчик покупателя требует `authorized_user` и принимает соединение с `user_id=42`. У `/api/support/ws/manager/{chat_id}` своя проверка на `authorized_manager`. Отсутствие токена, ошибка JWT или чужая роль закрывают соединение с кодом **1008**.

6. **Алиса входит на телефоне с паролем, затем привязывает Google на планшете.** `POST /api/users/login` передаёт `CustomerLoginREQT` (модель Pydantic с email и паролем) в `CustomerAuthenticationUC.login(user_data)`. `get_by_email_and_active(email="alice@example.com")` ищет активного покупателя, а `user_check_password(client_password="Bookshop!42", hashed_password=user.password)` вызывает `bcrypt.checkpw`. Пароль совпадает и провайдера Google ещё нет. Сервис выдаёт новый код `"875042"` тем же путём, API возвращает **`200` с новым UUID сессии `S2`**. После ввода кода `POST /api/users/login/verify` вызывает `CustomerAuthorizationUC.login_confirm(user_data)`. Для `session_id=S2` и `otp="875042"` он повторяет общую проверку, загружает **активного** покупателя по `otp.owner`, удаляет OTP и выпускает пару токенов с новой refresh-сессией.

   На планшете `GET /api/users/oauth/google/login` вызывает `oauth.google.authorize_redirect(request, redirect_uri, scope="openid email profile")`. В `/api/users/oauth/google/callback` вызов `oauth.google.authorize_access_token(request)` обменивает код через Authlib. `google_callback_router` берёт `userinfo` (данные профиля из ответа OAuth) и требует `email_verified=True`. Он собирает `CustomerOauthREQT` (модель Pydantic) из `email`, `name` → `username`, `sub` → `oauth_id` (для Алисы `"google-42"`). `CustomerGoogleAuthorizationUC.authorize(user_data)` ищет покупателя через `CustomerSQLAlchemyREPO.get_by_email(user_data.email)`.

   | Запись по email | Решение `authorize` |
   |---|---|
   | Покупателя ещё нет | Создаёт `UserModel` с Google и `oauth_id`. `save` возвращает ORM-объект с присвоенным ID, а активность и роль покупателя берутся из значений по умолчанию модели. |
   | Покупатель есть, провайдера нет | У Алисы срабатывает эта ветка. `user_make_is_google(user, oauth_id="google-42")` записывает провайдера и ID, затем сервис фиксирует изменения. Парольный вход для Google-аккаунта отклоняется. Если привязать Google к неактивной записи, она сохранит статус, и проверка активности при refresh отклонит вход. |
   | Уже привязан Google | `is_invalid_google_account(user, oauth_id=…)` сверяет входящий `sub` с сохранённым. При совпадении вход продолжается, при расхождении возникает `GoogleAccountSecurityERR`. |
   | У записи другой OAuth-провайдер | `OAuthProviderMismatchERR`. |

   При успешной привязке `authorize` выпускает **только refresh**, регистрирует его через `JWTRefreshAuthSession.create` и возвращает роутеру. Callback ставит cookie и перенаправляет на `/`. На планшете access в `localStorage` пока отсутствует, поэтому при загрузке главной запускается `refreshAccessToken()`.

7. **Браузер обновляет access и ротирует refresh.** `refreshAccessTokenOnce()` делает `POST /api/users/token/refresh` с `credentials="include"` и `X-CSRF-Token`. Зависимость `get_jwt_refresh_cookie` проверяет подпись, срок и тип refresh JWT, а `csrf_protect` через `hmac.compare_digest` требует совпадения заголовка с `csrf_token` (**иначе `403`**).

   `JwtRefreshTokenUpdateUC.execute(refresh_token)` получает из JWT `sub="42"` и `jti` сессии планшета. `JWTRefreshAuthSession.is_exists(jti)` через `RedisClient.key.exists` проверяет ключ. Затем `CustomerSQLAlchemyREPO.get_by_id(42)` через `AsyncSession` загружает аккаунт из PostgreSQL.

   | Условие | Действие `execute` |
   |---|---|
   | Ключ найден, Алиса активна | Удаляет прежнюю сессию, выпускает новый refresh с новым `jti`, сохраняет его и выдаёт access. Роль для access берётся из актуального `user.role` через `client_role_to_jwt_role`. Роутер заменяет обе cookie и возвращает access в JSON. |
   | Валидный refresh, ключа `jti` нет | Считает это **повторным использованием**. Вызывает `remove_all_user_sessions(user_id="42")`, удаляя ключи по списку сессий и сам список, затем возвращает ошибку `401` `JwtRefreshReplayDetectedERR`. |
   | Ключ найден, аккаунт отсутствует или отключён | Также удаляет все refresh-сессии, возвращает `403` `JwtInvalidERR`. |

   `refreshAccessTokenOnce` проверяет ожидаемую роль и сохраняет новый access, после чего на главной появляется «Выйти». Параллельные вызовы в одной странице ждут общий `accessTokenRefreshPromise` (объект Promise). Кроме загрузки страницы без access, `apiFetch` пробует refresh на **`401`** и один раз повторяет исходный запрос при успехе. Просроченный access в текущем коде превращается в `JwtInvalidERR` с **`403`**, поэтому этот ответ автоматический refresh через `apiFetch` не запускает.

8. **Алиса завершает сессии.** Logout проходит те же проверки refresh-cookie и CSRF. `CustomerLogoutUC` декодирует refresh и передаёт `sub` и, при необходимости, `jti` в `JWTRefreshAuthSession`.

   | Действие | Что удаляется в Redis |
   |---|---|
   | `POST /api/users/logout` → `from_device(refresh_token)` | `remove(user_id="42", jti=…)` удаляет ключ текущей сессии и её элемент в списке. Эту операцию вызывает кнопка «Выйти». |
   | `POST /api/users/logout/all` → `from_all_devices(refresh_token)` | `remove_all_user_sessions(user_id="42")` отзывает все refresh-сессии Алисы. |

   После `logout()` браузер удаляет локальный access и открывает `/`. `clear_auth_cookies` пишет заголовки во внедрённый `response`. Logout-роутер возвращает отдельный `Response(204)`, а при ошибке refresh обработчик исключений формирует отдельный JSON-ответ. Заголовки очистки cookie теряются. **Если при загрузке главной браузер автоматически отправит ещё действующую refresh-cookie уже удалённой сессии, сервер обработает её как повторное использование и отзовёт остальные сессии.** Выданные access-токены по-прежнему действуют до `exp` при обычной Bearer-проверке.
