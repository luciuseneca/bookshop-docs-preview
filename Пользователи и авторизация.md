# Пользователи и авторизация

PostgreSQL хранит аккаунт, хеш пароля, роль и признак активности. Redis хранит коды подтверждения и refresh-сессии. **Access-токен даёт доступ к API, refresh-токен позволяет получить новую пару токенов.**

## Регистрация и вход по email

- **Регистрация.** Покупатель вводит email, имя и пароль. Сервер сохраняет аккаунт с `is_active=False`. Если такой покупатель уже активен, регистрация отклоняется. Если он ещё не подтвердил email и текущий код истёк, можно повторить регистрацию с новым именем и паролем. Пароль хранится как bcrypt-хеш со случайной солью.
- **Вход.** Сервер ищет активного покупателя по email и проверяет пароль через `bcrypt.checkpw`. После проверки отправляет код. Для аккаунта, привязанного к Google, вход по паролю отклоняется.
- **Выдача кода.** Сервер генерирует шесть цифр через `secrets` и возвращает браузеру UUID `session_id`. В Redis две записи со сроком жизни 5 минут по примеру настроек. `email → session_id` позволяет найти действующий код и отклонить повторную выдачу с `409`, а `session_id → email и код` нужна для подтверждения. API ставит задачу Taskiq в RabbitMQ, воркер отправляет письмо по SMTP. Если письмо не доставлено, запись в Redis остаётся и продолжает блокировать повторную выдачу до истечения срока.
- **Подтверждение.** Браузер отправляет `session_id` и код. Отсутствующая запись считается истёкшей, неверный код даёт `400` и оставляет запись для повторной попытки. При подтверждении регистрации сервер сначала активирует аккаунт в PostgreSQL. При подтверждении входа он повторно проверяет, что покупатель активен. В обоих случаях сервер удаляет обе записи кода и выдаёт токены.

## Вход и привязка через Google

Authlib перенаправляет пользователя в Google и на callback обменивает код авторизации на токены Google. Приложение берёт из `userinfo` подтверждённый email и идентификатор Google-аккаунта `sub`.

- Новый email → создаётся активный покупатель без пароля.
- Email уже есть у покупателя без привязанного провайдера → к той же записи привязываются провайдер `google` и полученный `sub`. Например, история заказов сохраняется, потому что ID покупателя остаётся прежним.
- Google уже привязан → вход разрешён при совпадении `sub` с сохранённым `oauth_id`. Другой `sub` или другой сохранённый провайдер приводят к отказу.

Callback создаёт refresh-сессию, ставит cookie и перенаправляет на главную. При отсутствии локального access-токена страница получает его через refresh. Привязка сохраняет прежнее значение `is_active`, поэтому для ранее неактивного покупателя обновление токенов будет отклонено.

## JWT, ротация и выход

JWT подписываются приватным ключом RS256 и проверяются публичным. В обоих токенах есть тип, ID пользователя (`sub`), уникальный ID токена (`jti`) и срок действия. Access также содержит роль. В примере настроек access действует **10 минут**, refresh — **7 дней**.

В Redis ключ `refresh:<jti>` с TTL отмечает действующую сессию. Sorted set `user_refresh_sessions:<user_id>` хранит её `jti` с временем выдачи. При добавлении сессии на пределе лимита (3 в примере настроек) сервер удаляет самый старый элемент и его ключ. Ротация получает новое время выдачи. Истёкший ключ сессии может исчезнуть раньше элемента sorted set, поэтому лимит считается по индексу.

При refresh сервер проверяет подпись, срок и тип токена, затем ищет `jti` в Redis. Если запись есть, сервер читает пользователя из PostgreSQL. Для удалённого или неактивного аккаунта он отзывает все refresh-сессии и отклоняет запрос. Для активного удаляет старый `jti`, сохраняет новый и выдаёт пару токенов с актуальной ролью в access. Проверка и замена `jti` идут отдельными командами Redis, поэтому параллельные запросы могут пройти проверку одного токена до его удаления.

**Пример.** Браузер обменял `R1` на `R2`. Если позже снова прислать ещё не просроченный `R1`, сервер увидит, что его `jti` исчез, сочтёт это повторным использованием, удалит все refresh-сессии пользователя, включая `R2`, и вернёт `401`. Так же обрабатывается ещё действующий JWT вытесненной сессии. Обычный выход удаляет из Redis сессию по `jti` токена из cookie, выход везде — все refresh-сессии пользователя. Уже выданные access-токены действуют до своего `exp` на маршрутах, которые проверяют только JWT.

## Cookie и браузер

Access хранится в `localStorage` и передаётся как `Authorization: Bearer …`. У витрины и панели менеджера разные ключи `localStorage`, а refresh-cookie общая. У неё `HttpOnly`, `SameSite=Strict` и путь `/api/users/`. Вместе с refresh сервер выставляет отдельную читаемую cookie `csrf_token`. Для refresh и обоих вариантов выхода JavaScript копирует её значение в `X-CSRF-Token`. Сервер сравнивает cookie и заголовок через `hmac.compare_digest`, при несовпадении возвращает `403`.

Браузер запрашивает refresh при загрузке страницы, если access отсутствует, и один раз повторяет API-запрос после `401`, если обновление удалось. Запросы одной страницы ждут общий `Promise`, чтобы не обменивать один refresh несколько раз. Между вкладками такой координации нет. **Особенность реализации.** Просроченный access сейчас даёт `403`, поэтому эта ветка автообновления при истечении срока не срабатывает. При выходе браузер удаляет локальный access. Сервер вызывает удаление cookie при выходе и ошибках ротации, но в этих ветках клиент получает другой объект ответа без этих заголовков удаления.

## Роли и WebSocket

- **Покупатель** получает роль `authorized_user` для корзины, заказов, отзывов и клиентского чата.
- **Менеджер** входит через панель поддержки по email и паролю без кода. Получает `authorized_manager`. Защищённые HTTP-операции панели дополнительно сверяют актуальную роль и активность в БД.
- **Администратор** входит в SQLAdmin по email и паролю. Панель хранит `admin_id` в отдельной сессии и при проверке снова читает роль и активность из БД.

В чате сервер проверяет access-токен при подключении WebSocket. Обычный клиент передаёт его в `Authorization: Bearer`, браузер использует `?token=…`. Сервер проверяет подпись, срок, тип и нужную роль для клиентского или менеджерского канала. Проверка JWT выполняется при открытии соединения, поэтому истечение токена само по себе не закрывает уже открытый сокет.
