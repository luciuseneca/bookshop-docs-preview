# Пользователи и авторизация

## Возможности

Покупатель может создать аккаунт по email, имени и паролю. Первый код из письма активирует аккаунт и сразу открывает витрину, а при следующих входах с паролем нужно подтверждать каждый вход новым кодом. Через Google можно создать аккаунт или привязать существующий аккаунт с тем же подтверждённым email.

Сессия покупателя или менеджера состоит из короткоживущего access-токена для API и refresh-токена для продления доступа. Можно войти на нескольких устройствах. В витрине есть кнопка «Выйти», а API также позволяет отозвать все сессии. Покупатель может открыть чат поддержки, менеджер работает с обращениями в своей панели, администратор управляет аккаунтами через SQLAdmin.

## Сквозной сценарий (E2E)

Анна регистрируется на ноутбуке, входит с телефона и домашнего компьютера, открывает чат поддержки, а затем привязывает Google на планшете. В примере PostgreSQL присваивает Анне `id=42`, а `R1`, `R2` и далее обозначают выданные ей refresh-токены. Пути, сроки жизни и лимит сессий приведены для `.env.example` из проверенной версии проекта. [Исходники FastAPI Bookshop, коммит `e281be0`](https://github.com/luciuseneca/fastapi-bookshop/tree/e281be01f267ee0a3215f61e1cf6312b33434ba6)

### 1. Анна заполняет форму регистрации

На странице `/auth` Анна выбирает «Регистрация» и вводит `Anna@example.com`, `anna_books` и `Books42!`. JavaScript убирает пробелы по краям email и имени и отправляет `POST /api/users/register` с JSON-полями `email`, `username` и `password`. FastAPI передаёт тело в `CustomerRegisterREQT` (модель Pydantic). Валидатор переводит email в нижний регистр и проверяет длину части до `@` от 3 до 50 символов. Имя должно содержать от 3 до 20 символов, а пароль от 8 до 70, включая заглавную и строчную латинские буквы, цифру и спецсимвол из `#?!@$%^&*-`.

`CustomerAuthenticationUC.register(user_data)` вызывает `get_by_email(email="anna@example.com")`. Репозиторий SQLAlchemy ищет в `users` (таблица PostgreSQL) запись с ролью `customer`, сравнивая адреса в нижнем регистре. Для активного покупателя ответ сразу `409`. Для нового адреса или неактивного покупателя сервер сначала проверяет, есть ли действующий код, через `OtpAuthSession.get_by_owner(owner="anna@example.com")`.

У Анны записи ещё нет. `user_hash_password(password="Books42!")` кодирует пароль в байты, вызывает `bcrypt.hashpw(password.encode(), bcrypt.gensalt())` и возвращает хеш строкой. Случайная соль входит в сам хеш, поэтому два одинаковых пароля при регистрации обычно дают разные значения. Сервер сохраняет `UserModel` (ORM-модель SQLAlchemy) с `email="anna@example.com"`, `username="anna_books"`, этим хешем, `role=customer` и `is_active=False`. `save(new_model)` вызывает `AsyncSession.merge()`, `flush()` и `refresh()`, а `_transaction.commit()` фиксирует запись до выдачи кода. Пока аккаунт не активирован, обычный вход его не найдёт. Если Анна прервёт регистрацию, после истечения кода она сможет снова указать имя и пароль. Сервис обновит поля существующей неактивной записи.

### 2. Redis хранит код, а воркер отправляет письмо

Сервис вызывает `otp_generate_session_id()` и получает `uuid.uuid4()`, например `0c5ec697-db9c-4a9c-b743-534560c8e77c`. `generate_otp()` выбирает каждую цифру через `secrets.choice(string.digits)` и возвращает строку, например `042719`. Вызов использует аргумент по умолчанию `length=6`. `OtpAuthSession.create(new_otp)` принимает `OtpDTO` (неизменяемый Python `dataclass`) с полями `owner="anna@example.com"`, `code="042719"`, `session_id` с этим UUID и `ttl=300` из настроек.

| Ключ и тип | Значение и назначение |
| --- | --- |
| `otp:0c5ec697-db9c-4a9c-b743-534560c8e77c` (строка Redis с JSON-объектом) | Поля `owner`, `code`, `session_id` и исходный `ttl`. По UUID из формы сервер найдёт email и код. |
| `otp:anna@example.com` (строка Redis с UUID) | Указывает на ту же запись. По email сервер найдёт действующий код при следующем запросе на выдачу. |

Для обоих ключей используется `SET` с `ex=300`. `get_by_owner(owner)` сначала делает `GET` по email, затем по найденному UUID. Пока запись кода доступна, сервис возвращает `409` при повторной выдаче. Поэтому Анна не получит новое письмо при повторном нажатии «Продолжить» в течение этих пяти минут, если первый запрос уже сохранил код. Проверка и запись выполняются отдельными командами. При одновременных запросах ограничение по email не атомарно.

После записи в Redis API вызывает `await send_otp_email.kiq(user_data.email, new_otp.code)` с `anna@example.com` и `042719`. Taskiq через `AioPikaBroker(settings.rabbitmq.url, delayed_message_exchange_plugin=True)` публикует задачу в RabbitMQ. Как только публикация завершена, API отвечает `201` с сообщением и `session_id`. Браузер сохраняет UUID в переменной страницы и показывает поле «Код из письма». Этот ответ подтверждает постановку задачи в очередь. В частности, если SMTP позже откажет, форма уже будет открыта, а повторная выдача останется ограниченной до истечения ключа.

Отдельный процесс `taskiq worker app.shared.service.infrastructure.taskiq.broker:taskiq_broker` выполняет `send_otp_email(email="anna@example.com", otp="042719")`. Задача вызывает `send_letter_to_email(body=..., subject="Код подтверждения", send_from=settings.smtp.default_email, send_to=email)`. В теле письма будут `Ваш код: 042719` и срок `settings.otp.ttl // 60`, то есть 5 минут. `MIMEText` формирует письмо в UTF-8. Для SMTP из примера `smtplib.SMTP(host, port)` подключается к серверу, `starttls()` включает шифрование, `login()` использует данные из DSN, а `sendmail()` передаёт письмо почтовому серверу. Для `smtps` используется `SMTP_SSL`. В успешном сценарии Анна находит код во входящих. Если отправка падает, воркер логирует ошибку и поднимает исключение. У задачи нет метки автоматического повтора, а код остаётся в Redis. Если сбоит сама публикация, успешного HTTP-ответа уже не будет, но ключи Redis созданы раньше.

### 3. Код активирует аккаунт и даёт первую пару JWT

Анна вводит `042719`. Браузер отправляет `POST /api/users/register/verify` с `session_id="0c5ec697-db9c-4a9c-b743-534560c8e77c"` и `otp="042719"`. В `CustomerAuthConfirmREQT` (модель Pydantic) первый параметр преобразуется в `UUID`, второй остаётся строкой с ведущим нулём.

`CustomerAuthorizationUC.register_confirm(user_data)` вызывает `_get_valid_otp(user_data)`. `OtpAuthSession.get(session_id)` читает ключ UUID и запрашивает оставшийся `TTL` у Redis. Истечение определяется по отсутствию записи при чтении. Если код истёк или уже был использован, сервер возвращает `400` с `the confirmation code expired`. Если Анна ввела `042718`, ответ тоже `400`, но с `incorrect confirmation code`, а запись сохраняется для следующей попытки.

По `otp.owner` сервис вновь читает покупателя из PostgreSQL. Для отсутствующего или уже активного покупателя возвращает `404`. Для Анны `user_make_active(user)` меняет `is_active` на `True` и записывает текущее время UTC в `created_at`. После `save()` и `commit()` сервер вызывает `OtpAuthSession.delete(otp)`, который удаляет оба ключа одной командой `DEL`. Следующий последовательный запрос с этим UUID уже не подтвердит регистрацию.

`_jwt_tokens(user_id="42")` передаёт в `JWTGenerator.access_token(token_data=JWTAccessTokenDTO(sub="42", role="authorized_user"))` данные access-токена, а в `JWTGenerator.refresh_token(token_data=JWTRefreshTokenDTO(sub="42"))` данные `R1`. Эти DTO (Python `dataclass`) создают отдельные UUID для `jti` каждого токена. Генератор добавляет `type` со значением `access_token` или `refresh_token`. `jwt_encode(payload, exp_timedelta)` добавляет `iat` и `exp` в секундах Unix и подписывает данные через `jwt.encode(..., algorithm="RS256")` из PyJWT приватным ключом. При чтении `jwt.decode(token, load_public_key(), algorithms=[settings.jwt.algorithm])` проверяет подпись и срок. По настройкам из примера access выдаётся на 10 минут, refresh на 7 дней. Роль есть в access. Роль для новой пары при продлении сервер берёт из базы.

### 4. Сервер записывает refresh-сессию, браузер открывает витрину

Сервис декодирует `R1`, достаёт `jti` и вызывает `JWTRefreshAuthSession.create(user_id="42", jti=<UUID из R1>, ttl=604800)`. Сначала он проверяет число сессий через `ZCARD`. Затем `SET` с `ex=604800` сохраняет `refresh:<jti>` (строка Redis со значением `42`), а `ZADD` добавляет `jti` с оценкой `time.time()` в `user_refresh_sessions:42` (сортированное множество Redis). `EXPIRE` задаёт срок жизни индекса в те же 7 дней. За счёт первой записи сервер проверяет, разрешён ли обмен конкретного refresh, а индекс позволяет перечислить сессии пользователя и найти самую старую.

API отвечает `200` с `JwtAccessTokenRESP` (модель Pydantic с `access_token` и `token_type="Bearer"`). `set_auth_cookies(response, refresh_token=R1)` отправляет две cookie. У `refresh_token` заданы `HttpOnly`, `SameSite=Strict`, `Path=/api/users/` и `Max-Age=604800`. JavaScript не может прочитать эту cookie. Для `csrf_token` сервер генерирует значение через `secrets.token_urlsafe(32)`, задаёт `SameSite=Lax`, `Path=/` и такой же `Max-Age`. Эту cookie JavaScript читает. Для обеих в коде задано `secure=False`.

Браузер кладёт access под ключом `access_token` в `localStorage` (хранилище браузера) и открывает адрес из `next` или `/`. В шапке Анна видит «Выйти». При запросе корзины `GET /api/books/cart/by/user` функция `apiFetch()` подставляет `Authorization: Bearer …`. FastAPI через `HTTPBearer(auto_error=False)` и `auth_client` проверяет JWT и требует `role="authorized_user"`. `CustomerAuthorizedREQT` (модель Pydantic) преобразует `sub="42"` в число, и корзина читается по `user_id=42`. Та же зависимость ограничивает доступ к избранному, заказам и записи отзывов. JWT менеджера с другой ролью на этих маршрутах даёт `403`.

### 5. Анна входит с телефона и домашнего компьютера

На каждом устройстве `POST /api/users/login` принимает `email="anna@example.com"` и `password="Books42!"` через `CustomerLoginREQT` (модель Pydantic с теми же проверками email и пароля). `CustomerAuthenticationUC.login(user_data)` запрашивает `get_by_email_and_active(email=user_data.email)`. SQLAlchemy фильтрует по `is_active=True` и `role=customer`. Затем `user_check_password(client_password=user_data.password, hashed_password=user.password)` вызывает `bcrypt.checkpw()` с байтами введённого пароля и сохранённого хеша. Несовпадение пароля или отсутствие подходящего покупателя даёт `401`.

При верном пароле сервер выдаёт код по шагу 2, на этот раз с HTTP-ответом `200`. Анна сначала подтверждает телефон кодом `318507`, затем домашний компьютер новым кодом `651804`. Каждый запрос `POST /api/users/login/verify` передаёт свой `session_id` и введённый `otp`. `login_confirm(user_data)` проверяет код, снова ищет активного покупателя по `otp.owner`, удаляет запись OTP и выдаёт токены как на шагах 3–4. Повторный запрос активности нужен на случай, если аккаунт отключили между проверкой пароля и вводом кода. Теперь у Анны три refresh-сессии в порядке выдачи `R1` (ноутбук), `R2` (телефон) и `R3` (домашний компьютер).

### 6. Телефон восстанавливает доступ и меняет refresh-токен

В примере на телефоне пропала запись `access_token` из `localStorage`, а cookie сохранились. При открытии страницы `getToken() || await refreshAccessToken()` запускает `fetch("/api/users/token/refresh", {method: "POST", credentials: "include", headers: csrfHeaders()})`. Браузер прикладывает `R2` как cookie, а `csrfHeaders()` читает `csrf_token` через `document.cookie` и копирует значение в `X-CSRF-Token`.

На сервере `get_jwt_refresh_cookie(request)` извлекает cookie, проверяет JWT и требует `type="refresh_token"`. Отдельная зависимость `csrf_protect(request)` применяет double-submit проверку. Она вызывает `hmac.compare_digest(cookie_token, header_token)` и возвращает `403`, если значения расходятся или одного нет. Браузер прикладывает refresh-cookie автоматически, поэтому сервер дополнительно требует значение, которое JavaScript прочитал и передал в заголовке. Эти же зависимости работают на обоих маршрутах выхода.

`JwtRefreshTokenUpdateUC.execute(refresh_token=R2)` разбирает `sub="42"` и `jti` и проверяет `EXISTS refresh:<jti>`. Если сессия есть, `get_by_id(int(user_id))` читает актуального пользователя из PostgreSQL. Для удалённой или неактивной записи сервер отзывает все refresh-сессии аккаунта и отвечает `403`. В нашем случае Анна активна. Сервис удаляет ключ `R2` и его элемент в индексе через `DEL` и `ZREM`, создаёт и сохраняет `R2′` с новым `jti` и новым сроком. Затем выпускает access с ролью из `client_role_to_jwt_role(user.role)`. Для `manager` маппинг даёт `authorized_manager`, для текущего `customer` срабатывает значение по умолчанию `authorized_user`. Ответ заменяет обе cookie и отдаёт access в JSON. Анна остаётся авторизованной, а порядок сессий теперь `R1`, `R3`, `R2′`.

Браузер также пытается обновить токен при `401` от `apiFetch()`. Если обмен удался, исходный запрос повторяется один раз. Параллельные запросы одной страницы ждут общий `accessTokenRefreshPromise` (JavaScript `Promise`). Если каждый запрос отправил бы свою копию `R2`, первый обмен мог бы удалить его прежде, чем второй дошёл до проверки сессии. Между вкладками общего `Promise` нет. На сервере чтение, удаление и создание сессии тоже идут отдельными командами. При ошибке refresh браузер очищает локальный access. У истёкшего access есть особенность. `is_valid_jwt_access_token()` переводит исключение PyJWT в `JwtInvalidERR` с кодом `403`, поэтому ни истечение, ни перезагрузка страницы с ещё сохранённым токеном сами по себе этот обмен не запускают. `getToken()` смотрит на роль, срок JWT он не проверяет.

### 7. Анна открывает чат, а менеджер подключается из своей панели

Виджет на телефоне открывает WebSocket по `/api/support/ws?token=…`, передавая access в query-параметре. Клиент с поддержкой произвольных заголовков может передать `Authorization: Bearer …`, у которого в `auth_user_ws(websocket)` приоритет. Функция проверяет подпись, срок и тип JWT. Маршрут покупателя требует `authorized_user`, маршрут менеджера требует `authorized_manager`. Если токен отсутствует, недействителен или выдан для другой роли, сервер вызывает `websocket.close(code=1008)` до `accept()`. После успешного подключения срок JWT в цикле обработки сообщений больше не проверяется.

По `sub="42"` сервер вызывает `get_or_create_user_chat(user_id=42)`. Метод читает чат из кэша Redis или ищет открытый чат в `chats` (таблица PostgreSQL). Если чата ещё нет, создаёт его, например `id=17`, с `user_id=42` и `manager_id=None`. `get_user_chat_history(user_id=42)` читает `chat_messages` (таблица PostgreSQL), связывая сообщения с чатами покупателя по `chat_id`, и сортирует их по `created_at`. Сервер отправляет событие `history` (JSON-объект с `data.messages`). Для пустой истории виджет показывает приглашение написать в чат.

Олег на другом устройстве открывает `/support/manager`. Его форма отправляет `POST /api/support/manager/login` с `email="oleg@example.com"` и его паролем. `ManagerLoginREQT` (модель Pydantic) приводит email к нижнему регистру и убирает крайние пробелы. `ManagerLoginUC.execute(login_data)` вызывает `get_by_email(email="oleg@example.com")` с фильтром `role=manager`, проверяет активность, наличие хеша и пароль через bcrypt. При успехе сразу выдаёт пару JWT с `role="authorized_manager"` в access и создаёт refresh-сессию. Такой вход проходит без OTP. Панель хранит access под ключом `manager_access_token`. У панели и витрины разные ключи `localStorage`. В одном профиле браузера обе страницы используют общие refresh- и CSRF-cookie. При успешном refresh браузер применяет новые cookie, даже если JavaScript затем отбросит access из-за несовпадения роли со страницей.

Панель Олега запрашивает `GET /api/support/manager/chats?status=queue`. `get_current_manager(payload, db)` требует менеджерскую роль в JWT, затем читает `db.get(UserModel, int(payload.sub))` и сверяет текущую роль и активность в базе. В очереди видны открытые чаты с `manager_id=None`, среди них чат Анны. При выборе чата панель запрашивает `GET /api/support/manager/chats/17/messages?limit=50&offset=0`, затем открывает `/api/support/ws/manager/17?token=…`. После проверки JWT и `accept()` сервер пытается взять `schat:manager-lock:17` (строка Redis с UUID подключения) через `SET` с `nx=True` и `ex=3600`. Если ключ уже есть, соединение закрывается. Так второе подключение к тому же чату не перезапишет блокировку первого.

`AssignManagerToChatUC.execute(manager_id=7, chat_id=17)` ищет Олега по ID с фильтром `role=manager` и читает открытый чат. Этот поиск по WebSocket проверяет роль в БД. Проверка `is_active` есть у HTTP-зависимости панели. При первом подключении сервис сохраняет `manager_id=7`, сбрасывает кэш чата Анны и публикует в `schat:17` (канал Redis Pub/Sub) событие `system`. Сервер пересылает его виджету, и Анна видит «Олег подключился к чату и готов помочь», а Олег может отвечать. Если чат закреплён за другим менеджером, WebSocket закрывается. При переподключении того же менеджера событие о назначении не повторяется.

### 8. Администратор проверяет аккаунт в своей панели

Администратор Ирина открывает `/admin/` и входит через форму SQLAdmin. `AdminAuth.login(request)` читает `email` и `password` из `await request.form()`, ищет точное совпадение по `UserModel.email` в PostgreSQL и проверяет `is_active`, `role=admin` и пароль через `user_check_password()`. При успехе записывает `admin_id` (строковое поле подписанной сессии Starlette) со значением ID Ирины через `request.session.update()`. SQLAdmin подключает `SessionMiddleware` с секретом приложения. При каждом защищённом запросе `authenticate(request)` снова читает администратора из БД по `admin_id`. При выходе `request.session.clear()` очищает сессию панели. [Механизм сессии SQLAdmin](https://github.com/smithyhq/sqladmin/blob/0.32.0/sqladmin/authentication.py)

Ирина находит Анну по email в разделе Users и видит активного покупателя. В этой панели можно изменить роль и `is_active`. Например, если Ирина снимет признак активности, при следующем продлении с действующей refresh-сессией сработает проверка PostgreSQL из шага 6. Для уже выданного access на маршрутах витрины проверка ограничена JWT, поэтому деактивация сама по себе его не прерывает. В основном сценарии Ирина только проверяет запись.

### 9. Анна входит через Google на планшете и вытесняет старейшую сессию

Кнопка на `/auth` открывает `GET /api/users/oauth/google/login`. FastAPI строит адрес обратного вызова через `request.url_for("google_callback")`. Клиент Authlib зарегистрирован как `google` с `client_id`, `client_secret` и `server_metadata_url` из настроек. Вызов `oauth.google.authorize_redirect(request, redirect_uri, scope="openid email profile")` отправляет Анну в Google. Клиент настроен на `response_type="code"`. На `GET /api/users/oauth/google/callback` вызов `oauth.google.authorize_access_token(request)` обменивает код, полученный от Google, на токены провайдера.

Приложение берёт `token["userinfo"]` (объект профиля OpenID Connect). При `email_verified=False` возвращается `400`. С подтверждённым email в `CustomerOauthREQT` (модель Pydantic) передаются `email="anna@example.com"`, `oauth_id="g123"` из `sub` и `username="Anna"` из `name`. `CustomerGoogleAuthorizationUC.authorize(user_data)` находит покупателя по email. При первой привязке `user_make_is_google(user, oauth_id="g123")` меняет только `oauth_provider` на `google` и `oauth_id` на `g123`, после чего выполняется `commit()`. Анна сохраняет `id=42` и связанные с ним данные. Хеш пароля тоже остаётся в записи, но `login()` для Google-аккаунта отклоняет парольный вход с `401`. Если запись была неактивной, привязка сохранит этот статус, и последующий refresh завершится отказом. Другой уже сохранённый провайдер даёт `409`.

Для Анны создаётся `R4` с `sub="42"`. В `JWTRefreshAuthSession.create()` счётчик `ZCARD` уже равен лимиту `settings.auth.max_auth_user_sessions=3`. `ZRANGE` с `start=0, stop=0` находит `jti` токена `R1`, после чего `remove(user_id="42", jti=<UUID из R1>)` удаляет его ключ и запись в индексе. Только затем сохраняется `R4`. Порядок определяется временем последней выдачи refresh. Поэтому телефон с недавно выданным `R2′` сохраняет сессию. Если отдельный ключ истёк, пока общий индекс ещё живёт, `ZCARD` может учитывать оставшийся в индексе `jti`. Проверка наличия конкретной сессии по `EXISTS` в таком случае уже даст отрицательный результат.

Callback выставляет cookie с `R4` и перенаправляет на `/`. На планшете ещё нет access-токена. При загрузке главной страницы браузер выполняет обмен из шага 6, заменяет `R4` на `R4′`, получает access и показывает Анне витрину. В Redis теперь `R3`, `R2′` и `R4′`. С ноутбука продлить `R1` уже нельзя. Если JWT ещё действует и запрос доходит до проверки Redis, его отсутствие обрабатывается по правилу повторного использования из примера ниже.

### 10. Анна завершает сессию

Анна нажимает «Выйти» на планшете. `logout(everywhere=false)` вызывает `POST /api/users/logout` с `R4′` и CSRF-заголовком. `CustomerLogoutUC.from_device(refresh_token=R4′)` декодирует JWT и вызывает `remove(user_id=payload.sub, jti=payload.jti)`. После ответа `204` браузер удаляет локальный access через `clearToken()` и переходит на `/`.

Для завершения на всех устройствах предусмотрен `POST /api/users/logout/all` с такими же проверками. В JS этому соответствует `logout(true)`. Кнопка в шапке вызывает обычный выход. `from_all_devices(refresh_token)` берёт `sub` из JWT и передаёт в `remove_all_user_sessions(user_id=payload.sub)`. Метод получает все `jti` командой `ZRANGE` с границами `0, -1`, удаляет их ключи `refresh:<jti>` и сам индекс. Операция возвращает `204`. Уже выданные access-токены продолжают работать до истечения срока на маршрутах, которые проверяют только JWT.

У обоих выходов есть особенность ответа. `clear_auth_cookies(response)` выставляет заголовки удаления на переданном объекте, но обработчик возвращает новый `Response(status_code=204)`. Заголовки не доходят до браузера. Поэтому в нашем сценарии главная после обычного выхода видит пустой `localStorage`, пробует обменять оставшийся `R4′` и получает `401` за повторное использование. Сервер при этом отзывает и `R3`, и `R2′`, а на планшете появляется «Войти». При ошибке ротации заголовки удаления также теряются, поскольку обработчик исключений создаёт собственный JSON-ответ.

## Другие случаи

1. **Первый вход через Google и проверка привязки.** Если Google вернул `email="elena@example.com"`, `email_verified=True`, `name="Elena"` и `sub="g456"`, а в базе такого email нет, сервис создаёт покупателя с `is_active=True` и `password=NULL`. За оба значения отвечают настройки ORM-модели. Сервис берёт присвоенный ID из объекта, возвращённого `save()`, после `merge()` и `flush()`. Он выдаёт refresh, а access появляется на витрине после обмена. При повторном входе с тем же email и `sub="g456"` используются прежняя запись и её ID. Если при том же email приходит `sub="g999"`, `is_invalid_google_account(user, oauth_id="g999")` сравнивает его с сохранённым `oauth_id="g456"`. Callback отвечает `403` с `google account identity mismatch detected` и не выдаёт сессию. Проверка удерживает привязку к конкретной учётной записи Google даже при совпадении email.
2. **Повторное использование refresh после ротации.** Если сразу после шага 6 приходит повторный запрос с ещё действующим `R2`, сессии по его `jti` уже нет. `JwtRefreshTokenUpdateUC.execute()` вызывает `remove_all_user_sessions(user_id="42")`, удаляя в том числе новый `R2′` и независимые сессии `R1` и `R3`. Ответ `401` содержит `refresh token replay detected`. Так сервер прекращает дальнейшее продление всех сессий после повторного предъявления выданного токена. Код использует один признак для повторного, вытесненного и отозванного refresh, а именно отсутствие его ключа. Просроченный JWT отклоняется раньше, при декодировании cookie, поэтому до отзыва остальных сессий дело не доходит.
