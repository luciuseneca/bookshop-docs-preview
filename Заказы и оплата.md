# Заказы и оплата

## Что умеет

Авторизованный покупатель может оплатить картой выбранные книги или всю корзину. На странице корзины кнопка «Оформить заказ» отправляет отмеченные позиции в `POST /api/orders`. Этот же маршрут принимает явный список книг от API-клиента. `POST /api/orders/from-cart` принимает запрос без списка и сам читает всю корзину из `carts` и `cart_items` (таблицы PostgreSQL). Оба маршрута используют один сценарий оформления. Книги резервируются сразу, а результат оплаты сообщает Stripe.

## Покупка двух экземпляров книги №42

1. **Ввод.** Покупатель отмечает книгу №42 с количеством 2 и оставляет другую книгу неотмеченной. В `items` (JSON-массиве позиций) должно быть от 1 до 10 записей, в каждой `quantity` (целое число) больше нуля. Браузер отправляет `{"items":[{"book_id":42,"quantity":2}]}`. Неверное тело прямого запроса даёт `422`. Покупка всей пустой корзины или корзины с более чем 10 позициями даёт `400`.
2. **Резерв и сумма.** PostgreSQL читает строки из `books` (таблица PostgreSQL) по возрастанию ID через `SELECT … FOR UPDATE NOWAIT`. Под блокировкой сервис проверяет, что книга существует, доступна для продажи и её остатка хватает. Если на складе 3 экземпляра по 12,50, доступный остаток уменьшается до 1. В той же транзакции сервис создаёт заказ №101 в `orders` (таблица PostgreSQL), фиксирует базовую цену единицы в `order_items` (таблица PostgreSQL) и записывает платёж №77 в `payments` (таблица PostgreSQL). Сумму считает через `Decimal` по формуле «цена × количество» для каждой позиции, без применения скидки. Здесь итог 25,00, оба статуса `pending`. Коммит сохраняет резерв и освобождает блокировки.
3. **Ссылка на оплату.** После коммита сервис запускает синхронный SDK Stripe через `asyncio.to_thread`. Создаёт клиента Stripe по имени пользователя и email, затем сессию Checkout в режиме `payment` для карты. Передаёт название, количество и цену в центах USD, здесь 1250 центов за штуку. **Корзина показывает 25 ₽, а Stripe выставляет $25**, потому что код передаёт то же число без конвертации. Сессия действует 30 минут по умолчанию. В `metadata` (словарь метаданных Stripe) передаются строковые `order_id` и `payment_id`. Ключ `payment_77` защищает создание сессии на стороне Stripe для этого платежа. Повтор всего запроса оформления при достаточном остатке создаст новый заказ, платёж и ключ. Отдельная транзакция сохраняет ID сессии в `payments.transaction_id`. API возвращает `201` с `checkout_url`, браузер открывает Stripe Checkout.
4. **Подтверждение.** После оплаты Stripe отправляет `POST /api/orders/webhook`. SDK проверяет исходные байты тела и заголовок `Stripe-Signature` с секретом webhook. Неверная подпись или тело дают `400`. По `checkout.session.completed` сервер берёт ID из метаданных и одной транзакцией ставит платежу `success`, заказу `paid`, сохраняет `payment_intent` в `payments.payment_intent_id` и удаляет из корзины всю позицию книги №42 по её ID. Неотмеченная книга остаётся в корзине, доступный остаток №42 равен 1. Если Stripe повторит событие после коммита, обработчик увидит `success` и завершится сразу. На обработанное или неиспользуемое событие API отвечает `{"status":"ok"}`.
5. **Что видит покупатель.** При возврате из Stripe `GET /api/orders/success?order_id=101` показывает JSON с сообщением «Заказ 101 успешно оплачен!». При переходе по ссылке отмены `GET /api/orders/cancel?order_id=101` показывает «Оплата заказа 101 отменена». Оба маршрута формируют текст из параметра URL. Статус оплаты обновляет webhook.

## Если заказ не дошёл до оплаты

- **Книг не хватило или их оформляют параллельно.** Если другой запрос держит блокировку книги №42, `NOWAIT` сразу даёт ошибку блокировки, а API отвечает `409`. Если после первого заказа доступен 1 экземпляр, следующий прямой запрос на 2 тоже получит `409`. Та же ошибка возникает для отсутствующей или недоступной книги. Если до ошибки успели уменьшить остаток другой книги из списка, транзакция откатит и это изменение.
- **Покупатель вышел из Stripe.** После перехода на `/cancel` заказ №101 ещё `pending`. При `checkout.session.expired` сервер отменяет заказ, если он всё ещё `pending`, и в одной транзакции выставляет `canceled`, переводит платёж в `failed`, если у него ещё нет `success`, и прибавляет 2 экземпляра под блокировкой строк книг. В примере остаток возвращается с 1 до 3. Повтор события после коммита видит `canceled` и пропускает заказ.

  Параллельные обработчики могут увидеть прежний статус, поскольку читают заказ и платёж без блокировки их строк. Запоздалый `completed` способен перевести отменённый заказ в `paid` после возврата книг. При подтверждении обработчик доверяет типу подписанного события и отдельно не проверяет `payment_status`.

- **Stripe недоступен или webhook потерялся.** Если создание клиента или сессии выбросило исключение, сервер вызывает ту же отмену и при её успехе возвращает `502`. Если отмена тоже сорвалась, процесс остановился после резерва или событие истечения не дошло, есть запасной путь. Каждые 10 минут планировщик Taskiq отправляет задачу через RabbitMQ. Воркер выбирает до 100 заказов в `pending` старше срока Checkout плюс 10 минут, по умолчанию старше 40 минут от создания заказа. Он отменяет каждый отдельно по состоянию в PostgreSQL. При ошибке транзакция этого заказа откатывается, а заказ может попасть в следующую выборку.

При покупке всей корзины и при отмене SQLAlchemy загружает книги ещё до запроса с блокировкой. Если другая транзакция обновит остаток между двумя чтениями, запрос с блокировкой может вернуть уже загруженный объект со старым количеством. [Документация SQLAlchemy об обновлении загруженных объектов](https://docs.sqlalchemy.org/en/20/orm/session_basics.html#expiring-refreshing)
